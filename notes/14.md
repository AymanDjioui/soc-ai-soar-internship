# Session Log — 2026-08-04 (cont.) — A1: SSDP Suppression + a Real Week-Long Redis Outage Found Along the Way

## 🎯 Objective

ROADMAP Task A1 — kill the SSDP false-positive flood that's been creating a new TheHive
case every ~5 minutes from the Windows LAN host's normal UPnP discovery traffic
(originally found in `notes/12.md`). Verify it live, not just "should be working."

---

## ✅ What was accomplished

### 1. Baseline captured before touching anything

| Metric | Value |
|---|---|
| Total historical alerts, SID 2019102 (`ET DOS Possible SSDP Amplification Scan in Progress`) | 543 |
| Alerts in the last 7 days | 79 |
| TheHive cases created from this single signature | **39** |

That's 39 cases — out of the total case volume — from one confirmed-benign signature.
A real, quantifiable noise problem, not a hypothetical one.

### 2. Fixed via pfSense's native Suricata Suppress List (not a raw file edit)

Confirmed `threshold-file` was already wired into the LAN (`em1`) instance's
`suricata.yaml` but pointed at an empty file — the plumbing existed, nothing was using
it yet.

Used **Services → Suricata → Suppress** (a proper GUI feature, not a workaround) to
create a named list `lan_ssdp_noise` containing:
```
suppress gen_id 1, sig_id 2019102, track by_src, ip 192.168.10.30
```
Then assigned that list to the LAN instance under **Interfaces → LAN → Alert
Suppression and Filtering**. This suppresses the signature only for this specific
already-investigated-and-confirmed-benign host — genuine SSDP amplification scans from
any other source are still fully detected. Consistent with the project's standing rule
of using pfSense's own GUI/API for Suricata changes, never raw `config.xml` edits.

### 3. Live-tested against real traffic — found and fixed a real gap along the way

Rather than waiting for Windows to organically retrigger its own SSDP broadcast, pulled
the exact rule content for SID 2019102 (`content:"M-SEARCH * HTTP/1.1"` +
`ST: ssdp:all\r\n` to UDP/1900, threshold `count 2, seconds 60`) and reproduced it
precisely via a PowerShell `UdpClient` script run over WinRM against the real Windows
LAN VM (now reachable again after re-registering on Tailscale with a new IP,
`100.101.109.12` — the old `100.92.104.99` identity is dead).

**First test run — alert still fired despite the suppress config being saved.**
Root-caused properly rather than assumed: the em1 Suricata process (PID `46500`) had
been running continuously since `09:05` that morning — pfSense's GUI "Save" on the
Suppress List assignment page updates the on-disk config but does **not** restart the
running process, and Suricata does not hot-reload `threshold.config`. Confirmed via
`ps` (same PID, same start time, before and after the "Save").

**Fix:** manually stopped and restarted just the LAN instance via **Services → Suricata
→ Interfaces** (the pause/play icons on that row) — a fresh PID (`1307`, started
`16:20`) confirmed the reload actually happened this time.

**Second live test, after the real restart:** zero alerts of any kind for the SSDP
traffic. To make sure "zero" meant "correctly suppressed" and not "sensor silently
broken," separately confirmed the same host was still generating normal alerts for an
unrelated signature (`ET INFO STUN Binding Request`, background WebRTC/NAT-traversal
noise) in the exact same time window — proving the sensor was alive and selectively
suppressing only the intended signature+host pair, not failing silently.

### 4. Found, along the way: a full week-long silent Redis-on-pfSense outage

While debugging why the *first* suppress test didn't behave as expected, checked
whether the whole pipeline was even flowing normally — it wasn't. **The most recent
event across all three Suricata interfaces (WAN/DMZ/LAN) was from `2026-07-28`, seven
days stale.** `redis-cli ping` on pfSense returned `Connection refused`; Redis was not
running at all.

This is the exact same recurring failure already flagged in `ROADMAP.md` §1.3 item 3
(Redis on pfSense not surviving reboot) — now its **third documented occurrence**
(see `notes/9.md`, `notes/12.md`). This time it went undiscovered for a full week
because nothing was watching for it — the exact gap ROADMAP Task A2 exists to close.

**Fix:** `service redis start` on pfSense, verified with a real protocol-level `PING` →
`PONG` (not the package's own status indicator, which has lied before — see
`notes/11.md`). Confirmed the whole platform resumed ingesting within ~10 seconds of
the restart, across all three interfaces, not just LAN.

**Not caused by anything done in this session** — the outage predates today by days;
we simply happened to test at the moment it would have been discovered regardless.

## ⚠️ Known issues / follow-ups

1. **A2 (pipeline watchdogs) is now the single highest-priority remaining item.** This
   is the third silent, week-plus Redis-on-pfSense outage in this project's history.
   Each time it's been found by accident. An ElastAlert "no `suricata-alerts-*` events
   in N minutes" dead-man rule would have caught this in minutes instead of a week.
2. **Windows LAN VM's Tailscale identity changed** (`100.92.104.99` → `100.101.109.12`)
   — it re-registered as a new node rather than resuming its old one. `CLAUDE.md` /
   any saved references to the old IP need updating.
3. **pfSense Suricata's Suppress List GUI does not restart the affected instance on
   save** — worth remembering for any future suppress/threshold changes: always
   manually stop/start the specific interface afterward and verify with a fresh PID,
   don't assume "Save" was sufficient.
4. Consider whether Redis should be set to start automatically on pfSense boot
   (if the package/OS supports it) as a complement to A2's watchdog — prevention
   alongside detection, not detection alone.

## 🎤 Report angles unlocked today

- **"Verification found a bigger bug than the one we were looking for"** — testing the
  SSDP suppression fix (a minor tuning task) surfaced a platform-wide week-long
  detection outage that would otherwise have gone unnoticed indefinitely. A clean
  example of why live verification matters even for "should be working" changes.
- **"The GUI's Save button lied by omission"** — same family of lesson as
  `service redis status` reporting "not running" while the process answered `PING`
  (`notes/11.md`): a config UI can save correctly without the running system ever
  reflecting the change, and the only way to know is to test the actual behavior, not
  trust the save confirmation.
- **"Third strike on the same bug is a pattern, not bad luck"** — Redis-on-pfSense not
  surviving reboot has now silently broken detection three separate times across this
  project. That repetition is itself the strongest possible argument for A2's
  watchdogs in the report — this is empirically the project's biggest operational risk,
  not a theoretical one.
- **"Suppressed, not blinded"** — the fix scoped narrowly to one signature+host pair,
  leaving genuine SSDP amplification detection fully intact for any other source. Worth
  a sentence distinguishing tuning-out-a-known-false-positive from disabling detection.
