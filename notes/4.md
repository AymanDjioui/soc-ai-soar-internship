## The gap — what "real SOC" needs on top of this

A working SIEM needs more than "data is queryable in Discover." An analyst also needs:

- **Dashboards** — glanceable operational awareness
- **Enrichment** — turn raw IPs into context (geo, ASN, reputation)
- **Multiple data sources** — pfSense alone is not a SOC
- **Alerting rules** — proactive notification when patterns match
- **Documented detections** — repeatable, understood, defensible
- **Proof of detection** — actual simulated attacks that show the whole chain firing

The tasks below close this gap in priority order.

## Priority 1 — GeoIP enrichment 🌍

**Why:** Right now `45.159.97.61` is just a number in your data. Adding GeoIP tags every IP with country, city, ASN, and coordinates. Unlocks map visualizations in Kibana (huge visual win for the report) and makes your data look genuinely SIEM-grade. This should be done **before** dashboards so the maps have data to render.

**Effort:** ~30 min

**What to do:**

1. Download MaxMind GeoLite2 City database (free, requires MaxMind account signup)
2. Copy the `.mmdb` file into the Logstash container's volume (e.g. `~/elk-stack/logstash/geoip/GeoLite2-City.mmdb`)
3. Mount it in `docker-compose.yml`
4. Add a `geoip { source => "src_ip" target => "geoip_src" ... }` filter to `logstash.conf` for both syslog and suricata_eve types
5. Restart Logstash, confirm new fields appear (`geoip_src.country_name`, `geoip_src.location`, etc.)

**Definition of done:**

- Kibana Discover shows new `geoip_src.*` fields on new events
- `geoip_src.location` recognized as a geo_point by Elasticsearch (enables maps)

**Report angle:** "Enriched raw network telemetry with geolocation metadata for contextual analysis."

**Definition of done:**

## Priority 3 — Add Filebeat auth log source 🔑

**Why:** Right now pfSense is your only log source, which makes for a thin architecture diagram. Adding Ubuntu SSH auth logs from `devoteam` itself:

- Adds a second source to the diagram
- Enables SSH brute force detection scenarios
- Uses the port 5044 Logstash listener you already set up but haven't used
- Sets up naturally for later "Auth Logs" dashboard

**Effort:** 30-60 min

**What to do:**

1. Install Filebeat 8.15.0 on `devoteam` (matching ELK version)
2. Enable the built-in `system` module (auth log ingestion out of the box)
3. Point Filebeat output at `localhost:5044` (Logstash Beats input)
4. Add a Logstash filter branch for `type == "beat_auth"` if any parsing needed (usually the module handles it)
5. Route to a new index `auth-logs-YYYY.MM.DD`
6. Create a Kibana data view `auth-logs-*`

**Definition of done:**

- SSH login/failure events from `devoteam` appear in Kibana within seconds
- Fields present: `source.ip`, `user.name`, `event.outcome` (success/failure), `process.name` (sshd)

**Report angle:** "Log aggregation from heterogeneous sources: network appliance (pfSense syslog), IDS (Suricata TCP JSON), and server auth (Filebeat)."

## Priority 4 — Kibana alerting rules 🚨

**Why:** Detection isn't real if it's silent. Kibana native alerting fires proactively without needing TheHive — and later, these same rules can be the trigger for TheHive alerts.

**Effort:** 1-2 hours

**Prerequisite:** Priority 3 done (need auth logs for the brute-force rule to make sense).

**Rules to build:**

1. **Port scan detection**: `soc-logs-*` where >50 blocked events from same `src_ip` within 5 minutes
2. **High-severity Suricata alert**: `suricata-alerts-*` where `event_type:alert` and `alert.severity <= 2` (severity is inverted — lower = more severe)
3. **SSH brute force**: `auth-logs-*` where >10 failed auth from same `source.ip` within 5 minutes
4. **Repeat offender**: `soc-logs-*` where same `src_ip` shows up in blocks across ≥3 consecutive hours

**Definition of done:**

- Each rule created in Kibana Stack Management → Rules and Connectors
- Each rule tested with real or simulated data
- Each rule has an action (initially just an in-Kibana alert; later will hook to TheHive)

**Report angle:** "Automated detection logic layered above raw telemetry — reduces analyst mean-time-to-notice."

## Priority 5 — Pipeline polish 🧹

**Why:** Small things that make the setup look professional rather than "cobbled together." Not urgent, but if a graded evaluator opens the config files, these details matter.

**Effort:** ~1-1.5 hours total (each item is 15-30 min)

**Items:**

- [ ] **User-Agent parsing** on Suricata HTTP alerts. Add a `useragent { source => "http.http_user_agent" }` filter so `curl/8.11.0` becomes `{name: curl, version: 8.11.0, device: Other}`.
- [ ] **Remove duplicate `event.original`** on Suricata events. Currently the raw JSON stays in ES _and_ the parsed fields — doubles storage. Add `mutate { remove_field => ["[event][original]"] }` after the `json` filter.
- [ ] **ICMP field alignment fix** in the filterlog CSV. Current filter assumes TCP/UDP layout — ICMP events misalign because filterlog uses `icmp_type`/`icmp_code` instead of ports. Add a conditional grok branch for `proto_id == "1"`.
- [ ] **Add index lifecycle policies (ILM)** for `soc-logs-*` and `suricata-alerts-*` and `auth-logs-*` — rollover after 30 days, delete after 90. Prevents your VM from filling up over time.
- [ ] **Set `target` on `csv` and `json` filters** — Logstash warns about this on startup. Fixes an ECS compliance warning that's currently harmless but ugly in logs.

**Definition of done:** All items checked off, `docker compose logs logstash | grep -i warn` shows fewer warnings than before.

## Priority 6 — Attack simulation setup 🎯

**Why:** This is where "SOC lab" becomes "SOC lab that catches attacks." Every attack scenario becomes a defensible bullet in the report + a screenshot showing the detection.

**Effort:** Half-day for setup + separate time per scenario

**Prerequisite:** Need to design network topology first — PfSense currently has no client/victim VMs behind it, so there's no traffic actually flowing through the firewall for Suricata to catch. Attackers running outside PfSense won't be visible to it.

**What to build:**

1. **Victim VM** — DVWA (Damn Vulnerable Web App) or Metasploitable2 behind PfSense LAN
2. **Attacker VM** — Kali Linux (or minimal Debian with `nmap`, `hydra`, `curl`, `sqlmap`, `hping3` installed) somewhere it routes through PfSense to reach the victim
3. **PfSense config** — routing between LAN and OPT1 (or wherever attacker/victim sit), rules that log

**Scenarios to run (each = report screenshot):**

|Scenario|Tool|Expected detection|
|---|---|---|
|Port scan|`nmap -sS -sV <victim>`|`ET SCAN Nmap`-family alerts + block bursts in `soc-logs-*`|
|SSH brute force|`hydra -l root -P wordlist.txt ssh://<victim>`|Auth log failed-login spike (Priority 3+4 needed)|
|Web attack (SQLi)|`sqlmap -u http://<victim>/dvwa/vulnerabilities/sqli/`|Suricata `emerging-web_server` alerts|
|Known-bad traffic|`curl http://testmyids.com`|Already works — this is your baseline validated test|

**Definition of done:**

- Each scenario runs successfully
- Each generates the expected alert in Kibana
- Each has a screenshot showing the alert + relevant enrichment (geo, User-Agent, etc.)

**Report angle:** Chapter titled "Detection validation via simulated adversary activity" — this is what makes the writeup real, not theoretical.
