## 1. Moved the AI layer from CPU to GPU

The CPU host was the bottleneck. One triage call took 177.6 s, a full alert took 514 s,
and the 206 queued alerts in TheHive would have needed about 28 hours of inference.

### Getting a GPU was harder than expected

T4 capacity was **unavailable in four regions** (europe-west1, us-central1,
northamerica-northeast1, europe-west3). T4 is the cheapest GPU on GCP and is permanently
contended, and new accounts get low priority. Do not spend time chasing it.

Switched to **L4** and it provisioned immediately.

Also worth recording: the model most recommended online for security work,
`qwen3.6:35b`, needs **23.9 GB of weights on a 24 GB card**, so it does not fit at all.
`llama3.3:70b` needs 42.5 GB. Check VRAM before planning around a recommendation.

### Final host

```

Tailscale          100.90.228.58

Orchestrator       ~/soar (venv, user djiouiayman)
```

GCP blocks public port 22 by design, so always connect over the Tailscale IP.
`sudo tailscale up --ssh` avoided the whole SSH key problem, and it also avoids Google's
guest agent rewriting `~/.ssh/authorized_keys`.

### Measured speedup

| | CPU (EC2) | GPU (L4) |
|---|---|---|
| Triage, warm | 177.6 s | **2.5 s** |
| Full alert | 514 s | ~15-20 s |
| 206-alert backlog | ~28 h | **~20 min** |

Token throughput on the L4: **237 tok/s reading the prompt, 53 tok/s generating**.
Against the CPU host that is 18x and 33x.

**Cold start is 30 to 37 s** while the model loads into VRAM. Ollama unloads after idle,
so the first request after a break always pays it. Warm the model before any demo:

```bash
curl -s http://100.90.228.58:11434/api/generate \
  -d '{"model":"mistral:7b","prompt":"hi","stream":false}' > /dev/null
```

Diagnostic tip: the `load_duration` field in the response tells you which case you are in.
Near zero means warm, tens of seconds means it had been unloaded.

## 2. Golden set re-run on GPU: same score, different errors

19/21, identical to both CPU hosts. But **not the same failing cases**:

| Case | EC2 CPU | GPU L4 |
|---|---|---|
| 01-testmyids | severity correct | severity wrong |
| 03-attack-response | severity wrong, technique wrong | severity wrong, technique correct |

Output is deterministic **within** a host (three identical runs) but not **across** hosts,
even with identical weights, prompt, schema and `temperature=0`. CPU and GPU kernels take
different floating point paths and near-tie tokens resolve differently.

Consequence: a benchmark result belongs to model + prompt + schema **+ hardware**.
Changing the machine means re-running, not assuming. The earlier claim that "accuracy is
invariant to hardware" holds in aggregate but not case by case, and has been corrected in
`deployment-latency.md`.

### Four new findings (13 to 16, written into `model-benchmark.md` §9)

- **13. Finding 9 was overstated.** `qwen3:30b-a3b` returned an **empty string** after
  45.9 s. Not malformed JSON, no output at all. Constrained decoding guarantees that *if*
  content is emitted it conforms; it does not guarantee content is emitted. `call_llm()`
  already fails safe, but the guarantee needed correcting.
- **14. The enum field can contradict the model's own reasoning.** `qwen3.5:27b` emitted
  `T1547.001` while its own `technique_reasoning` named T1592; the right answer was T1046.
  Three techniques in one response. The enum forces a *valid* value, not a *considered* one.
- **15. Over-applying prompt context, in the dangerous direction.** `gemma4:12b` described
  an **external** scan as "internal administrator on our VPN" and marked it a false
  positive. It pattern-matched the network baseline instead of reading the alert. A false
  negative silently suppresses a real detection and no schema constraint catches it.
- **16. MoE did not help and latency is not size-ordered.** The MoE model scored lowest.
  `qwen3-coder:30b` (18 GB) answered in 2.4 s while `gemma4:12b` (7.6 GB) took 57.6 s.

## 8. A-2c: Windows brute force rule was broken (found by checking, not by symptom)

### The symptom was a red herring

TheHive showed alerts titled `New Service on {match[host.name]}` with 0 observables, and
I assumed the rule templates were broken. **They were not.** All live rule titles are
clean and were fixed on 2026-08-04. Those alerts are dated 28/07/2026, so they are stale
backlog from before that fix.

Lesson: alert content in the queue reflects the rule **at the time the alert was created**,
not the rule now. Check the rule file's mtime before concluding it is broken.

### But checking the fields found a real bug

Verified every field referenced by the six Windows rules against the live data. Five rules
were fine. `win_bruteforce.yaml` had four defects:

| # | Defect | Evidence |
|---|---|---|
| 1 | `query_key: source.ip` | `source.ip` exists in **0** documents. The IP is at `winlog.event_data.IpAddress` (608 docs) |
| 2 | Observable mapped `ip: source.ip` | alerts arrived with **no IP observable**, so Cortex had nothing to enrich and the orchestrator had no containment target |
| 3 | `alert_text_args` used `source.ip` | the Source IP line rendered empty |
| 4 | Filter matched event_id 4625 on any channel | Microsoft-Windows-EventSystem emits an unrelated 4625 on the Application channel. **4 of 11 matches were noise** |

Defect 1 is the serious one. A frequency rule with a non-existent `query_key` cannot group
by attacker, so "5 failed logons from the same source" was never being counted per source.
The rule looked deployed and healthy while not doing its job.

### The fix, and proof it works

Scoped to the Security channel, switched to `winlog.event_data.IpAddress.keyword`
(text field, so the `.keyword` subfield is required or grouping silently fails again),
excluded `IpAddress: "-"` which is what local logon failures report, and fixed the
observable and alert text mappings.

```
old filter: 11 documents  (4 unrelated Application events)
new filter:  7 documents  (all genuine Security failed logons)

grouping by attacker now works:
  fe80::69d0:eab6:705c:3b43   5 failures   <- reaches the threshold
  192.168.10.1                2 failures
```

The 5 failures are the Atomic Red Team `T1110.001` test. With the old rule they could not
be grouped, so the brute force detection would not have triggered on our own red team run.

Deployed, schema validated, ElastAlert restarted, 0 errors, all rules loading.

## 9. Pre-arming audit of the orchestrator

Read the whole file before tomorrow's armed run, since it will really modify the firewall.
Five findings, three fixed.

### Fixed: it could have blocked the victim instead of the attacker

`select_containment_target()` returned the first IP observable that passed the guard,
with **no notion of source versus destination**.

- Inbound (external -> internal): the external IP is the attacker. Correct.
- **Outbound (internal -> external): the external IP is the destination**, and it would
  have been selected and blocked.

Not hypothetical. Our own test case `04-powershell-ua` is `192.168.10.30 -> 217.160.0.187`.
Armed, against a queue of 206 alerts, this would have come up.

The role information already existed and was being ignored: `suricata_high_severity.yaml`
tags observables `src` and `dst`. Rules that do not tag (`pfsense_portscan.yaml`) list the
source first, so document order is the fallback.

Now: prefer `src`-tagged, else exclude `dst`-tagged, else document order. Verified on five
shapes. The outbound case now picks the internal source and the guard refuses it, so the
external destination is never touched.

### Fixed: the kill switch could silently not work

```python
KILL_SWITCH_FILE = "./KILL_SWITCH"      # relative to CWD
AUDIT_LOG        = "./soar_audit.jsonl" # relative to CWD
```

`touch KILL_SWITCH` in the wrong directory left containment **armed** while the operator
believed it was off. Worse, `recent_block_count()` reads the audit log, so a different
working directory **silently reset the rate limiter to zero**.

Both are now absolute, anchored next to the script, and printed in the startup banner.
Regression test: running from `/tmp` with the switch in `~/soar` is correctly detected as
ACTIVE and containment REFUSED.

A safety control that depends on which directory you were standing in is not a safety
control.

### Fixed: PROTECTED_ASSETS was out of date

Added `100.90.228.58` (the new GPU host). The CGNAT rule already covered it, so this is
defence in depth, but the list should describe the lab as it is.

An explicit banner when containment is live:

```
To stop it at any time:  touch /home/djiouiayman/soar/KILL_SWITCH
```

### Not fixed, lower risk

- **`confidence` has no bounds in the schema.** `{"type": "number"}` enforces the type but
  not the range, so a model returning `95` instead of `0.95` would pass the 0.75 threshold
  trivially. Constrained decoding cannot catch this. Worth adding min/max.
- **`recent_block_count()` can under-count.** The `try` wraps the whole loop, so one
  malformed record aborts counting and returns a partial total. The failure direction is
  permissive: fewer counted blocks means more blocks allowed.

### What held up under review

- `call_llm()` returns `None` on every failure path including empty output, so a failed
  model call can never yield a verdict. This is what makes the qwen3 empty-response case
  harmless.
- Containment only runs on `verdict == "malicious"`.
- `policy_guard()` ordering is correct and its reasons are accurate.
- Every refusal path is audited.
