# Session Log — 2026-08-04 — AI Layer: Model Selection, Benchmark, and Deployment (ROADMAP Task B1)

## 🎯 Objective

Stand up the AI/SOAR layer's foundation: pick a local LLM, prove it can do usable SOC
triage on real alerts from this lab, and decide where it runs. This is ROADMAP Task
B1 — the "cheapest point to discover the AI layer doesn't work," done deliberately
before any workflow (Shuffle/B2) is built on top of it. Zero dependency on Badr or the
lab VMs — done solo while Badr was offline.

---

## ✅ What was accomplished

### 1. Deployment research and initial VM setup

Researched current (2026) small/local LLM options for CPU inference before committing
to anything — `Phi-4-mini`, `Qwen3.5`, `Mistral 7B`, `Llama 3.1 8B` were the shortlist.
Also researched Ollama's schema-constrained `format` parameter (XGrammar under the
hood) as the mechanism to guarantee valid JSON output, avoiding an entire class of
"parse the model's prose" bugs.

**Decision on where to build/test:** a dedicated VM (`soc-llm`) on the laptop's
existing VMware setup, not inside the `soc-elk` VM (already running
Elasticsearch+Logstash+Kibana+ElastAlert2) and not Badr's AWS box (already fighting
OOM issues per his own report). 4 vCPU / 8 GB RAM / 48 GB disk, Ubuntu 24.04.

Real setup issues hit and fixed along the way:
- Ubuntu's installer defaulted the LVM root volume to 24 GB of the 50 GB disk —
  caught and fixed (`lvextend` + `resize2fs`) before it could bite mid-benchmark
  (4 models ≈ 14 GB).
- Ollama's install script needs a TTY for its internal `sudo` calls; ran the whole
  installer as root instead.
- `curl https://registry.ollama.ai/v2/library/<model>/tags/list` isn't public — model
  tag verification had to happen by pulling directly rather than querying first.

### 2. Golden test set — built from real lab history, not synthetic

7 real alerts pulled from `notes/3,7,10,11,12.md`, with ground truth known because we
ran the attacks ourselves. Deliberately **not** 7 obvious attacks:

| # | Case | Ground truth |
|---|---|---|
| 01 | testmyids canary, WAN | TP, medium, N/A technique |
| 02 | **SSDP false positive** (`notes/12.md`) — benign Windows UPnP → own gateway | **FP, must never auto-block** |
| 03 | GPL ATTACK_RESPONSE, external → LAN host | TP, medium |
| 04 | PowerShell UA signature (our own admin activity) | FP, informational |
| 05 | SQLi auth bypass → real admin JWT | TP, **critical**, T1190, source is Tailscale — must never auto-block |
| 06 | `reg save HKLM\SAM` (real cred dump, not blocked by Defender) | TP, high, T1003.002, host-based (no IP to block) |
| 07 | Nmap scan, DMZ, from Badr's Tailscale IP | TP, medium, T1046, must never auto-block (Tailscale CGNAT) |

**5 of 7 cases must never be auto-blocked** — because real attack traffic in this lab
routes through Tailscale (own admin access) or originates internally. That ratio alone
is a finding: a naive "AI says malicious → block" design would be wrong most of the
time here.

Built `ai/benchmark.py` — a harness that sends the golden set through any model/prompt/
schema combination via Ollama's chat API, scores against ground truth (3 pts/case:
false-positive call, severity, MITRE technique), and logs both a scored CSV and every
raw model response. Scoring was later split into a separate `rescore.py` so the scored
table can be regenerated from the immutable raw outputs without re-running inference.

### 3. Prompt iteration — v1 → v2 → v3, each version a real measured change

Full detail in `ai/results/prompt-iteration-log.md`. Summary:

- **v1 (zero-shot):** valid JSON worked perfectly, but the SSDP case was called
  malicious and the model invented CVE numbers instead of MITRE technique IDs.
- **v2 (few-shot, schema still included a `safe_to_auto_block` field):** few-shot
  examples caused the model to imitate the wrong pattern and **recommend auto-blocking
  our own internal Windows host** — the exact self-inflicted-outage scenario the
  guardrail design in ROADMAP §0.3 warns about, now reproduced as a measured result.
  **Architectural fix**: removed `safe_to_auto_block` from the model's schema entirely.
  Whether an IP may be blocked is deterministic policy (`policy_guard()` — RFC1918 /
  loopback / Tailscale CGNAT check), computed in code, never asked of the model. The
  model can inform; it cannot authorize containment.
- **v3 (zero-shot, safety field removed, rule-shaped baseline):** fixed the SSDP false
  positive (correct for the first time), but over-generalised "internal ⇒ benign" and
  produced two new false negatives (dismissed the credential dump and the Nmap scan as
  benign) — the precision/recall tradeoff, measured directly rather than assumed.

### 4. Model benchmark — 5 models, 4 configurations, 56 inferences

Full detail + all 10 findings in `ai/results/model-benchmark.md`. This directly answers
the encadrant's original instruction #3 (`notes/1.md`): *"make a benchmark of AI and
SOAR solutions"* — Badr's existing benchmark (`notes/badr_phase1_report (1).md` §6) is
literature-based; this one is measured, on our own alerts.

**Experiment 1 — model comparison** (fixed prompt/schema, model varies):

| Model | Params | Total | Latency |
|---|---|---|---|
| `mistral:7b` | 7B | 13/21 | 68.2s |
| `phi4-mini` | 3.8B | 13/21 | 24.1s |
| `llama3.1:8b` | 8B | 12/21 | 47.5s |
| `qwen2.5:7b` | 7B | 10/21 | 43.2s |
| `llama3.2:3b` | 3B | 5/21 (**mode collapse** — identical output for all 7 cases) | 19.6s |

Key results: parameter count did not predict performance (8B model scored lowest);
`mistral:7b` vs `qwen2.5:7b` — identical size, 30% apart, proving model *family* beats
size; `llama3.2:3b` broke down entirely below ~3.8B, establishing a capability floor.

**Experiment 2 — configuration tuning** (fixed model = `mistral:7b`, prompt/schema vary):

| Config | Total | Latency |
|---|---|---|
| zero-shot + free-form technique | 13/21 (62%) | 68.2s |
| zero-shot + enum-constrained technique | 14/21 (67%) | 85.0s |
| few-shot + free-form technique | 17/21 (81%) | 65.0s |
| **few-shot + enum-constrained** | **19/21 (90%)** | 74.1s |

**Configuration tuning gained 6 points; picking the best model over the 2nd-best
gained 1.** Prompt/schema engineering was ~6× more valuable than model selection —
the single most useful practical result for a time-constrained project.

Also found: the enum constraint stopped the model from inventing fake technique IDs
but couldn't force correct reasoning (only 1 extra point); an explicit `OTHER`
escape-hatch option for "I don't recognise this technique" was **never once selected in
21 opportunities** — models don't self-report uncertainty even when explicitly offered
the option, which matters directly for how B5's guardrails must be designed (inferred
externally, never requested politely).

**Decision: `mistral:7b` + few-shot + enum schema, 90% on the golden set.**

### 5. Deployment decision — tested, then reversed under realistic conditions

Full detail in `ai/results/deployment-latency.md`.

**Phase 1 (isolated benchmark):** tested the winning config on `soc-llm` (local VM, 4
physical cores) vs an EC2 `m7i-flex.large` (2 vCPU ≈ 1 physical core — the only instance
type available; `c6i.2xlarge` and other compute-optimized types are blocked outright by
this AWS account's free-tier restriction). Identical accuracy on both (confirms
`temperature=0` + identical model weights = deterministic regardless of hardware).
Local was 57% faster (74.1s vs 116.1s). **Initial decision: stay local.**

**Phase 1a (reversal):** re-ran the identical benchmark with `soc-elk` running
concurrently on the same 15 GB / 8-thread laptop — the actual daily condition, since
Kibana/pfSense dashboards need to be open in a browser continuously. Result: 124.5s
mean latency (+68% vs isolated), host swap hit 100% full, and (separately, same
session) a genuine host network/VM hang occurred requiring a hypervisor-level
intervention to recover. **Decision reversed: production inference moves to AWS.**
Not because EC2 is faster in isolation — it isn't — but because 116s uncontended beats
124.5s contended, and doesn't risk taking down the SIEM or the browser to get there.
Documented explicitly as a case where the first benchmark was correct on its own terms
but insufficiently representative of production conditions.

### 6. AWS EC2 provisioning and Tailscale integration

- `m7i-flex.large`, Ubuntu 24.04, eu-north-1, 20 GB gp3 — the only free-tier-eligible
  instance type with enough RAM (8 GB) to hold `mistral:7b` (4.4 GB) at all; smaller
  free-tier types (`t3.micro`/`t3.small`, 1–2 GB) can't even load the model.
- Real incident during setup: the very first inference run OOM-killed `llama-server`
  entirely (`Out of memory: Killed process (llama-server)`) — Ollama's default 5-minute
  model residency meant three models loaded back-to-back exceeded 8 GB. Fixed via
  systemd override (`OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_KEEP_ALIVE=60s`,
  `OLLAMA_NUM_PARALLEL=1`) — applied identically on both `soc-llm` and the EC2 box.
  Real sizing rule for the report: size for the *largest single model plus KV cache*,
  and cap concurrent residency explicitly; don't assume average load.
- **Tailscale added to the EC2 instance** (hostname `soc-llm-aws`, joined via a
  one-time, non-reusable, non-ephemeral auth key — no interactive browser approval
  needed on a headless box). Now reachable at a stable Tailscale IP
  (`100.96.231.95`) regardless of the instance's public IP, which changes on every
  stop/start since no Elastic IP is allocated (deliberately — avoids its small
  continuous cost for a mostly-stopped instance).
- Ollama was bound to `127.0.0.1` by default and refused connections over the
  Tailscale interface — fixed with `OLLAMA_HOST=0.0.0.0:11434` in the same systemd
  override. The AWS security group still only permits inbound SSH from an admin IP
  (kept as an explicit fallback, user's call), so the model endpoint itself is reachable
  **only** over the tailnet — same access-control pattern already used for Redis on
  pfSense (port 6379 scoped to one Tailscale IP).
- Verified end-to-end from the laptop: `curl` to `100.96.231.95:11434` → real model
  response ("Hello! How can I assist you today? 😊") — the exact path a future TheHive
  workflow will use.

### 7. Cleanup

- Removed the 4 benchmark-only models from `soc-llm` (kept only `mistral:7b`) — disk
  usage dropped 27 GB → 14 GB.
- Local `soc-llm` VM powered off by the user once the AWS endpoint was confirmed
  working, freeing the laptop for `soc-elk` + browser dashboard use.

## ⚠️ Known issues / follow-ups

1. **EC2 instance requires a manual start** before use — no auto-start, and stopping
   it (correctly, for cost control) means the public IP changes each time. Always
   connect via the Tailscale IP (`100.96.231.95`), not the public IP, to avoid this.
2. **Public SSH left open** on the EC2 security group (restricted to admin IP) as a
   deliberate fallback alongside Tailscale SSH — slightly larger attack surface than
   removing it entirely, kept by explicit user choice.
3. **GPU quota** (`g4dn.xlarge`) is blocked on this AWS account — worth requesting an
   increase ahead of the final demo purely as a latency option (~3-5s vs current
   ~74-124s), not because the AWS-vs-local decision is in question.
4. **Concurrent-load latency figure (124.5s) is n=1, informal** — browser tab count and
   other host state weren't controlled/logged. Qualitative result (severe degradation
   under concurrent load) is expected to replicate; the exact number is not.
5. B2/B3/B4/B5 (the actual triage workflow, autonomous trigger, and gated response
   loop) are **still entirely unbuilt** — this session closed out B1 only. That is the
   next and most important piece of work: the project's own name is "SOAR and AI," and
   nothing has yet actually acted on a real alert.

## 🎤 Report angles unlocked today

- **"We measured the AI recommending we block our own host"** — the v2 few-shot
  regression is a dated, reproducible, self-discovered justification for code-side
  guardrails, stronger than citing external literature.
- **"Configuration beat model choice 6-to-1"** — a genuinely useful, slightly
  counterintuitive result for a time-boxed project: where effort should go.
- **"The AI never admits it doesn't know"** — the 0-of-21 `OTHER` selection rate
  directly shapes how guardrails and escalation must be designed (external inference of
  uncertainty, not self-report).
- **"The first benchmark was right and still wrong"** — isolated local-vs-cloud testing
  said local wins; testing under the actual concurrent operating condition reversed the
  conclusion. A mature narrative about benchmark representativeness, not just a result.
- **"Capacity planning by failure"** — the OOM-kill on first concurrent EC2 run is a
  second, independent instance of this project's recurring pattern (see `notes/11,12.md`
  for VM clock drift, silent Redis death, etc.): infrastructure limits discovered by
  hitting them, then fixed and documented, not assumed in advance.
