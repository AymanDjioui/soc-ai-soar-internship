## 1. Tailscale STUN noise suppressed (~67% of all Suricata alerts)

Confirmed via Elasticsearch aggregation: SIDs `2016149` (STUN Binding Request, port
3478) and `2016150` (STUN Binding Response, port 41641) accounted for ~67% of all
`suricata-alerts-*` docs with `alert.signature_id` set (105,929 total alerts sampled,
70,566 were these two SIDs).

Added a pfSense Suricata suppress-list entry (`suppress gen_id 1, sig_id 2016149` /
`2016150`, no `track` clause — global suppression) via the GUI (Services > Suricata >
Suppress Lists).

**Discovery: pfSense actually runs *three* Suricata instances, not two.** WAN (em0)
and DMZ (em2) were documented in PROJECT-STATE.md; a **third instance on LAN (em1)**
was not. All the live STUN alert volume was coming from em1, not em0/em2 — suppressing
only WAN+DMZ had zero effect on the noise. Found by cross-referencing `in_iface` on
fresh alert docs against `ps aux` process list on pfSense. em1 was already running its
own suppress list (`lan_ssdp_noise`, added previously — presumably by Badr — for a
different SSDP false positive scoped to one internal IP). Added the two STUN suppress
lines to that existing list rather than reassigning em1 to a new list, to avoid losing
the existing SSDP suppression.

Verified fixed: STUN alert count in Elasticsearch dropped to 0 within the 5-minute
window following the em1 Suricata restart (last STUN alert at 10:34:30 UTC, restart at
10:35:20 UTC per `ps -o lstart`).

## 2. `pfsense_portscan.yaml` rewritten as a cardinality rule

Old rule: `type: frequency`, 10 events in 2 min from one `src_ip` where `reason:match`
— this matches almost *any* logged packet (pass or block), not actual port-scanning
behavior. It was flooding TheHive with SSDP/UPnP broadcast noise (2674 hits/24h) and
Juice Shop DNS lookups (484 hits/24h) misclassified as port scans.

New rule: `type: cardinality`, `cardinality_field: dst_port`, `min_cardinality: 15`
within 1 minute per `src_ip` — requires genuinely many distinct destination ports from
one source in a short window. Excludes Tailscale keepalive (`dst_port: 41641`) and
multicast (`dst_ip: 239.255.255.250`, `224.0.0.0/4`) via `must_not`.

## 3. Filterlog CSV parsing fixed for protocol-dependent column counts

pfSense's filterlog format has a different number of fields after `dst_ip` depending
on protocol (tcp: 9 extra fields incl. `tcp_flags`/seq/ack/window; udp: 3; icmp:
variable). The old Logstash config used one fixed 29-column mapping shaped for TCP,
silently misaligning ~197 records/24h for other protocols — producing garbage like
`src_ip: "RTALERT"` or `"0x0000"`.

Fix: `csv` filter now only parses the common prefix (through `dst_ip`), dumping the
remainder into a single `proto_data` field. A `ruby` filter then splits `proto_data`
and maps fields by name based on the actual `protocol` value (tcp/udp/icmp/other).

Verified on live traffic post-deploy: a real UDP SSDP packet
(`192.168.84.134:34180 -> 239.255.255.250:1900`) parsed cleanly with correct
`protocol: udp`, real `src_ip`, and correct ports — no garbage fields.

## 4. Stable `sourceRef` for TheHive dedup — and a bug caught mid-rollout

**The problem:** every ElastAlert hivealerter POST generated a random `uuid.uuid4()`
as `sourceRef`, so repeated firings of the same rule for the same source created a new
TheHive alert every time instead of merging into one.

**First obstacle:** elastalert2 2.19.0's bundled `HiveAlerter`
(`elastalert/alerters/thehive.py`) only runs the `{0}`/`{1}`-style arg-substitution
(`load_args`) on `description`, `title`, `type`, and `source` — not `sourceRef`. There
is no YAML-only way to make `sourceRef` dynamic per-match in this version. Patched the
installed file (copy kept in-repo at `configs/elk/elastalert/patches/thehive.py`,
mounted over the container's site-packages path via `docker-compose.yml`) to give
`sourceRef` the same `load_args` treatment, gated on an opt-in `sourceRef_args` key in
`hive_alert_config` (rules that don't set it keep the old random-uuid behavior,
unchanged).

Also added a `dedup_bucket` field in Logstash (global `ruby` filter, timestamp floored
to a 10-minute window, `%Y%m%d%H%M` string) so rules can build a stable ref like
`suricata-{signature_id}-{src_ip}-{dedup_bucket}`. Wired into
`suricata_high_severity.yaml`, `pfsense_portscan.yaml`, `pfsense_dmz_breakout.yaml`.

**The bug:** deployed, and within minutes `elastalert` logs showed a repeating
`400 Client Error: Bad Request` on every hivealerter POST. Reproduced directly against
TheHive's API with curl — POSTing the *same* `sourceRef` twice returns
`400 {"type":"CreateError","message":"Alert ... already exists in organisation
devoteam-soc"}`. **TheHive's `/api/alert` endpoint does not merge on duplicate
`sourceRef` — it hard-rejects the second POST.** My original design assumed
create-or-merge semantics that don't exist in this API/version. Net effect of the bug:
the *first* alert per source+signature+bucket still reached TheHive fine; only the
redundant repeats within the same 10-minute bucket errored — so no real detection was
lost, but the error loop needed fixing before it could be trusted.

**Fix:** catch the specific `400` + `"already exists"` response in the patched
`thehive.py` and log it as a successful dedup instead of raising — this is
functionally correct (TheHive already has an open alert for that source+signature+
bucket; the repeat carries no new information) without needing a real
merge/PATCH-based implementation. Verified live via a `Monitor` watch on the container
logs: subsequent duplicate-bucket alerts now log
`TheHive alert already exists for sourceRef=... - treating as deduped, not an error`
with no error surfaced.

## 5. SSDP false positive (same class as #1), and a real pipeline outage found along the way

While verifying #1's suppression, spotted a fresh TheHive alert for `ET DOS Possible
SSDP Amplification Scan in Progress` (SID `2019102`) from `192.168.10.20` -> `192.168.10.2`
(pfSense's own LAN gateway). Confirmed benign from the raw payload — a textbook UPnP
`M-SEARCH ssdp:discover` broadcast, not an actual amplification attempt (a real one
would show an external victim IP being flooded, not the LAN gateway receiving one
discovery packet). Same signature Badr had already partially suppressed
(`lan_ssdp_noise`, scoped `track by_src, ip 192.168.10.30` — a different host).
Widened it to a global suppress (dropped the `by_src` scoping) since this is a
device-discovery false positive regardless of which LAN host triggers it. Verified:
zero SID 2019102 alerts after the LAN Suricata restart.

Separately, a real watchdog alert fired: `PIPELINE DOWN: pfSense filterlog (soc-logs-*)
silent 30min`. Diagnosed methodically rather than reflex-restarting: `syslogd` process
running, `/var/log/filter.log` actively growing (pf itself logging fine locally),
network path pfSense->ELK:5514 confirmed open with a manual `nc` test, Logstash's UDP
5514 input confirmed working with a loopback test — yet `soc-logs-*` had received
nothing for ~85 minutes. Isolated to `syslogd` silently stopping *remote forwarding
only*, while continuing local logging — the identical failure mode as the 2026-08-06
incident already documented in the watchdog rule's own comments. Fixed immediately with
the rule's documented known-safe command
(`/usr/local/sbin/pfSsh.php playback svc restart syslogd`; confirmed the alternative,
`killall -HUP syslogd`, actually kills the daemon on this build rather than reloading it).

Since this is the second time this exact failure has occurred, a one-off restart isn't
a real fix. Added a pfSense cron job (`Services > Cron`, GUI-managed so it survives
config regen) restarting `syslogd` every 20 minutes
(`/usr/local/sbin/pfSsh.php playback svc restart syslogd`), capping any future silent
stall at 20 min instead of unbounded-until-a-human-notices. Confirmed present in both
`/etc/crontab` and `config.xml` (`<cron><item>`). The existing 30-minute watchdog rule
stays in place as a backstop — if it fires now, it means the auto-heal itself broke,
which is a real signal rather than routine maintenance.

## 6. Enrichment-summary fix — send Cortex's distilled taxonomy tags, not raw JSON

Item 6 in PROJECT-STATE.md's not-done list. `assess_enrichment()` (Phase 3, the
post-enrichment verdict call) was being handed the full raw Cortex analyzer report per
observable — a raw VirusTotal report alone runs to tens of KB of per-vendor scan
results the model has no real use for. Cortex already computes a distilled
`summary.taxonomies` list per report (e.g. `VT:GetReport=0/91`, `AbuseIPDB:Score=0`)
that was being extracted and printed to console for humans but never actually sent to
the model. PROJECT-STATE.md's own prior note flagged this as the likely cause of C-1's
verdict flip-flopping (same alert, different runs) during 2026-08-11 testing.

Fix in `soar/e2e_soc_orchestrator.py` (~line 916): the `reports` list built during
Phase 2 enrichment now stores only `{observable, analyzer, taxonomies}` per successful
analyzer job instead of `{observable, analyzer, report}` (the full raw dict). Nothing
else in the file consumed the raw `report` field — checked with `grep -n reports` —
so this is a clean substitution, not a partial fix.

Verified end-to-end against the real GPU-hosted `mistral:7b` (not just `py_compile`):
called `assess_enrichment()` directly with synthetic taxonomy-shaped data for a
clearly-malicious IP, bypassing TheHive/Cortex entirely to avoid creating a real case
or burning VirusTotal/AbuseIPDB API quota just to test a payload-shape change. Payload
size: 563 bytes (vs. multi-KB raw JSON). LLM returned a correct, schema-valid verdict
(`malicious`, confidence 0.97) that correctly cited the specific taxonomy values in its
reasoning. Synced to the GPU VM's `~/soar/e2e_soc_orchestrator.py` (old version backed
up first as `.bak-<timestamp>-enrichment-fix`); checksums confirmed matching
(`3f37a3af8ff438ae970cb2d74cdad75d`) between repo and VM after sync.

## 7. TheHive alert/case backlog cleanup

With the STUN/SSDP/portscan noise fixed at the source, the *historical* backlog in
TheHive was still 246 unprocessed alerts / 164 cases, mostly the same noise from
before the fix. Quantified via the `/api/v1/query` API rather than guessing:
`ET DOS Possible SSDP Amplification Scan in Progress` (120 alerts / 30 cases) and the
pre-fix broken `pfsense_portscan` rule (110 alerts / 1 case, every one of them with an
unformatted description — a separate pre-existing bug, `{0}`/`{1}` placeholders never
substituted, not something touched today) together made up 52% of all alerts ever
created and 73% of what was still sitting in "New". Initially left `LOCAL Possible
Port Scan Detected` (40 alerts / 11 cases, a different Suricata rule) out of scope
pending verification — see below, it turned out to be noise too and was folded in.

Chose `Ignored` (alerts) / `FalsePositive` (cases) over deletion — reversible, keeps
the audit trail, and this is Badr's shared instance too. Discovered this TheHive
instance uses a custom case-status taxonomy (`FalsePositive`/`TruePositive`/
`Duplicated`/etc. as direct `status` values, not TheHive's default `Resolved` +
separate `resolutionStatus`) via `/api/v1/describe/case` — the first attempt with
`"status":"Resolved"` 404'd. Verified both endpoints on one alert + one case before
batch-applying to the other 213.

Result: 183 alerts -> `Ignored`, 31 cases -> `FalsePositive`, zero failures. Active
"New" alert queue dropped from 246 to 74 (63 expected remainder + 11 genuinely new
alerts that arrived naturally during the ~15 min cleanup window — confirms the live
pipeline kept running throughout, nothing stalled).

## 8. `LOCAL Possible Port Scan Detected` (SID 9000001) — also confirmed noise

Followed up on the item left out of §7. Pulled sample alerts: every one showed
`192.168.84.134` (pfSense's own WAN IP) making single, ordinary one-packet outbound
TCP connections to different external IPs on port 80 — not scan-shaped traffic.
Confirmed by reading the actual rule in `custom.rules` on the WAN (em0) Suricata
instance:

```
alert tcp any any -> any any (msg:"LOCAL Possible Port Scan Detected";
  flags:S; threshold:type both, track by_src, count 15, seconds 30;
  classtype:attempted-recon; sid:9000001; rev:1;)
```

Same bug class as the original broken `pfsense_portscan.yaml`: counts raw SYN packets
by source within a window, with no check on whether they went to one destination
(an actual scan) or many (completely normal browsing/API/update traffic). A custom
local rule (SID in the `9000000+` local range, not an ET signature) — present only on
the WAN (em0) instance's `custom.rules`, confirmed absent from LAN/em1 and DMZ/em2.
Also functionally redundant now: today's fixed `pfsense_portscan.yaml` cardinality
rule already covers real port-scan detection properly at the filterlog layer.

Suppressed via the same `tailscale_stun_noise` list (WAN-only, matching where the rule
actually runs): added `suppress gen_id 1, sig_id 9000001` alongside the existing STUN
lines. Verified zero new alerts for this SID after the WAN Suricata restart. Cleaned
up the historical backlog the same way as §7: 21 alerts -> `Ignored`, 11 cases ->
`FalsePositive`, zero failures.
