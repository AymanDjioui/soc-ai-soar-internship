# Session 17 - 2026-08-11

All VMs up: ELK, pfSense/Suricata, TheHive/Cortex (Badr), GPU LLM host.
Goal was C-1 (a real autonomous block). **Not achieved**, but four significant bugs
were found and fixed, and the responder chain is now proven working.

## 1. The Suricata -> TheHive bridge was dropping 100% of alerts

Fired testmyids from pfSense. Suricata detected it correctly
(`GPL ATTACK_RESPONSE id check returned root`, SID 2100498, src 217.160.0.187).
It reached Elasticsearch. It never reached TheHive.

Diagnosis, from `elastalert_status_status`:

```
Suricata High Severity Alert   window 09:39:10 -> 09:44:10   hits=2  matches=0
silence: Suricata High Severity Alert  until 09:40:52
```

The rule **saw** the alert and produced no match, because it was inside a silence
window opened by unrelated traffic minutes earlier.

Cause: `realert: 5 minutes` with **no `query_key`**. Without a query key the silence
applies to the WHOLE RULE, not per source. Any chatty internal host keeps the window
permanently closed.

Measured impact that day:

```
qualifying Suricata alerts : 18
delivered to TheHive       :  0
```

Fix: `query_key: src_ip.keyword` (text field, so the `.keyword` subfield is required
or the grouping silently does nothing). After the fix the same attack came straight
through as alert `~122953976`.

**This is the same defect class as `win_bruteforce.yaml` yesterday.** Two rules, both
missing `query_key`, both looking perfectly healthy while not doing their job. Worth
its own paragraph in the report.

## 2. Triage never saw the observables

`alert.get("observables")` is not part of TheHive's alert response, so
`observables_count` was permanently 0 and the model was told there was no observable
data even when the alert carried two IPs.

The alert description is a flat block of text, so the model had to infer which address
was the attacker from prose.

Fix: fetch with `api.alert.find_observables()` and pass them into `triage_alert()`,
including each observable's `src`/`dst` role.

Effect on the same alert: `is_false_positive: True (0.75)` became
`is_false_positive: False (0.85)`.

### The bigger point

**The benchmark and production feed the model different things.**

| | golden test case 01 | what production sends |
|---|---|---|
| structure | JSON with `src_ip`, `dest_ip`, `in_iface` | flat text blob |
| signature id | present | absent |
| HTTP context | `hostname: testmyids.com`, user agent, url | **absent** |

So 19/21 on the golden set does **not** transfer to production, because the benchmark
measured a richer input than ElastAlert actually delivers. This belongs in the
benchmark report's limitations section.

## 3. The responder was called by name instead of its Cortex id

```
"responderId": "PfSense_Blocker_1_0"     <- a name
```

Cortex identifies workers by hash:

```
aebe07e932adfb592a20678599943378         <- confirmed in the Cortex API
```

Cortex rejected the job with `worker PfSense_Blocker_1_0 not found`.

Note the analyzer path was **always correct**: it lists the catalog, filters by name,
then sends `analyzer.get("id")`. The rule is **name to select, hash to call**. Only the
responder skipped the lookup.

Fix: `resolve_responder_id()` looks the id up by name at runtime. Resolving rather than
hardcoding also survives a Cortex reinstall, which changes the hash.

## 4. ⭐ The audit log claimed a block that never happened

The worst finding of the project so far.

```
10:19:56  audit:  containment_executed  target 217.160.0.187
10:19:56  Cortex: status=Failure  responder=-
                  "worker PfSense_Blocker_1_0 not found"
```

Same second, same observable. The script wrote **executed**; Cortex wrote **Failure**.
`EasyRuleBlockHostsWAN` was untouched.

Cause: `create_responder_action()` only **submits** the job. Cortex runs it
asynchronously and can fail afterwards. The code treated "request accepted" and
"action performed" as the same thing.

Fix: `wait_for_responder_action()` polls TheHive until Cortex reports `Success` or
`Failure`. Only `Success` writes `containment_executed`; anything else writes
`containment_unconfirmed` with the reason.

**An autonomous system that records actions it did not perform is more dangerous than
one that does nothing**, because you stop checking. This was invisible in every test
until someone looked at the firewall instead of the log.

## 6. Why C-1 is still not done

The full chain now runs end to end in ~65-75 s on the GPU, but it will not block
testmyids, and it is **right not to**:

| Analyzer | Result for 217.160.0.187 |
|---|---|
| VirusTotal | 0/91 engines |
| AbuseIPDB | score 0, reports 0 |
| URLhaus | no results |

`testmyids.com` is a legitimate IDS test site. The AI correctly returns `benign` and
containment is never reached.

Note one run *did* return `malicious 0.95` on the same IP ("Malwarebytes:
Trojan.Win32.Generic"). Minutes later the same lookup returned clean. **The threat feed
itself was inconsistent**, and the model followed the evidence both times.

To demonstrate a successful autonomous block we need an alert whose IP the threat feeds
genuinely flag. That means injecting a TheHive alert carrying a known-bad IP, labelled
honestly in the report as injected, because the lab produces no genuinely malicious
external traffic.
