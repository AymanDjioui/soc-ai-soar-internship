## Follow-up (2026-07-08 morning) — Cron watchdog forwarder solution

### Problem recurrence

The morning after the reboot, the forwarder was in a zombie state: `tail -F` and `nc` processes both showed in `ps` with the previous session's PIDs (13+ hours old, 0.16s total CPU), but no new data was reaching Kibana. Classic symptom of a broken TCP pipe that the process pair didn't detect. Confirmed the pattern: every pfSense reboot leaves the forwarder unusable until manually restarted.

### Approach — lightweight cron watchdog (chosen over daemon supervisor)

Rejected the earlier `daemon(8)` supervisor approach because it caused Tailscale to crash on service stop. Instead, used pfSense's built-in Cron package (already installed) to run a health-checking script every minute. Zero persistent supervisor process, zero risk to Tailscale.

### Implementation

**Cron entry** (added via Web UI → Services → Cron → Add):

|Field|Value|
|---|---|
|Minute|`*`|
|Hour|`*`|
|Day/Month/Weekday|`*` `*` `*`|
|User|`root`|
|Command|`/usr/local/etc/rc.d/suricata_forward.sh`|

**Rewritten `/usr/local/etc/rc.d/suricata_forward.sh`:**

```sh
#!/bin/sh
LOGSTASH_HOST="100.99.54.59"
LOGSTASH_PORT="5516"
LOG_FILE="/var/log/suricata_forward.log"

# Health check: does an nc process to Logstash currently exist?
if pgrep -f "nc ${LOGSTASH_HOST} ${LOGSTASH_PORT}" > /dev/null; then
    # Also verify it has an ESTABLISHED connection (not zombie)
    if sockstat -4 -c 2>&1 | grep "^root .* nc " | grep -q "${LOGSTASH_HOST}:${LOGSTASH_PORT}"; then
        exit 0
    fi
    # Process exists but no ESTABLISHED connection — kill it
    pkill -f "nc ${LOGSTASH_HOST} ${LOGSTASH_PORT}"
    pkill -f "tail -F .*eve.json"
    sleep 1
fi

# Find eve.json (folder ID may change on Suricata restart)
EVE_FILE=`ls /var/log/suricata/suricata_em0*/eve.json | head -1`
if [ -z "$EVE_FILE" ] || [ ! -f "$EVE_FILE" ]; then
    echo "`date`: eve.json not found" >> "$LOG_FILE"
    exit 1
fi

echo "`date`: starting forwarder on $EVE_FILE" >> "$LOG_FILE"
tail -F "$EVE_FILE" | nc "$LOGSTASH_HOST" "$LOGSTASH_PORT" >> "$LOG_FILE" 2>&1 &
```

### Health check logic (two-stage)

Stage 1 — `pgrep -f "nc ${LOGSTASH_HOST} ${LOGSTASH_PORT}"`: does the nc process exist at all?

Stage 2 — `sockstat -4 -c | grep "^root .* nc " | grep ${LOGSTASH_HOST}:${LOGSTASH_PORT}`: does that nc have an established TCP connection to Logstash? This catches the "zombie pipe" state where the process is alive but disconnected.

Only if both checks fail does the script kill stale processes and start a fresh forwarder.

### Verification tests performed

1. **Deduplication test**: ran the script twice in succession, confirmed same PIDs both times (20746, 20921). Health check correctly detected the existing forwarder and skipped restart.
2. **Kill+recovery test**: killed nc with `pkill -9`, waited 65 seconds, confirmed cron restarted a fresh forwarder with new PIDs.
3. **Testmyids alert**: `curl http://testmyids.com` from pfSense produced a Suricata alert visible in Kibana `suricata-alerts-*` within 15 seconds.

### Why this is safer than the daemon approach

- No persistent supervisor process → no fork/exec chain to interact with Tailscale
- Each cron run is a one-shot check; script exits in milliseconds when healthy
- Uses only base FreeBSD tools (`pgrep`, `sockstat`, `pkill`, `tail`, `nc`) already present on pfSense
- Reversible: disable in one click by deleting the cron entry via web UI

### Outcome

Forwarder now self-heals after reboot, network hiccup, Suricata restart, or Logstash restart, within a 60-second worst case. The recurring "every morning after reboot" manual restart problem is solved.

### Report angle

> **Forwarder resilience.** A cron-driven watchdog architecture was chosen over a daemon-supervised approach after the latter proved incompatible with the pfSense Tailscale package. The watchdog performs a two-stage liveness check every minute — process existence via `pgrep`, then TCP connection state via `sockstat` — restarting only when both checks fail. This design recovers from reboots and network faults within 60 seconds, cannot spawn duplicate forwarders, and introduces no persistent processes that could interact with other network daemons.
