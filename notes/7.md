### 4. Suricata EVE delivery — migrated from `tail|nc` script to native Redis output

The original forwarder (`tail -F eve.json | nc`, cron watchdog) was fragile by design — asked whether a more professional alternative existed. Compared:

- **Filebeat**: ruled out again (FreeBSD 15 ABI incompatibility, already documented).
- **Syslog**: Suricata's package does support it, but rejected — classic syslog (RFC3164) has a hard ~1024-byte message limit, and EVE alerts with payload/packet-dump data are several KB. Same class of failure as the UDP fragmentation problem already solved once before.
- **Redis**: chosen. Suricata's pfSense package already had unused Redis output fields in its config. Confirmed installable via `pkg install redis` (official pfSense repo, clean ABI match — unlike Filebeat).

**What was done:**
- Installed Redis on pfSense, bound to `127.0.0.1` + Tailscale IP `100.70.145.65`
- Added a `Firewall → Rules → Tailscale` rule scoping port 6379 to only the ELK VM's Tailscale IP (`100.99.54.59`)
- Added a `redis { }` input block to Logstash's pipeline, reusing the existing `suricata_eve` filter/output logic
- Switched both Suricata interfaces (WAN + DMZ) EVE Output Type from `FILE` to `REDIS`
- **Hit a real gap**: pfSense's Suricata package GUI has no Redis password field at all — every push was silently rejected (`rejected_calls` in Redis stats, `NOAUTH` errors in Suricata's log). Resolved by dropping `requirepass` and `protected-mode`, relying on the firewall rule alone for access control — a real security tradeoff, made consciously, not a workaround
- Retired the old forwarder: killed lingering `tail|nc` processes, removed the cron entry via `Services → Cron`, removed Logstash's now-dead `5515`(udp)/`5516`(tcp) inputs and the corresponding docker-compose port mappings
- **Verified end-to-end repeatedly**: WAN (testmyids, SID 2100498) and DMZ (XSS, SID 2009714) both confirmed flowing through Suricata → Redis → Logstash → Elasticsearch → Kibana

**Troubleshooting detour worth remembering**: mid-migration, DMZ alerts appeared to stop firing entirely (packet-level events logged fine, but no `alert` event type). Spent real effort checking rule content, HOME_NET/EXTERNAL_NET vars, rule-files lists — inconclusive. Root cause turned out to be simpler: Juice Shop itself had degraded (HTTP 502) from the earlier sqlmap heavy-query test and hadn't fully recovered. Once the app was healthy again, detection resumed immediately with zero config changes. **Lesson: check application health before assuming a detection-pipeline bug.**

**Final state confirmed live**: IDS Detections Dashboard showing 153 alerts, 9 unique signatures, spanning both WAN and DMZ sources, all through the new Redis pipeline.

### 5. Badr's Juice Shop HTTP logging (nginx-proxy) — fixed a real bug, one issue left open

Badr had already built a working-in-spirit pipeline on the Juice Shop DMZ box (`172.16.0.10`, also reachable directly via its own Tailscale identity `100.78.58.45`): an `nginx-proxy` container in front of Juice Shop logging structured JSON access logs, shipped via `rsyslog` (`imfile` → `omfwd` TCP) to Logstash's existing `juiceshop-docker` input (port 5517). This matches his own description in Darija — syslog/pfSense params were fine, but HTTP logs specifically weren't landing correctly.

**Bug found and fixed**: `juice-shop` container was started with plain `docker run` (no `--network` flag), landing it on the default `bridge` network, while `nginx-proxy` was on the purpose-built `js_net`. Docker's DNS-by-name only works within a shared user-defined network, so `nginx-proxy`'s `proxy_pass http://juice-shop:3000` never resolved correctly — nginx crashed, and all 5798 docs already in `juiceshop-docker-2026.07.16` were logged `502`s, not real traffic.

**Fix**: recreated both containers on `js_net` together. Verified end-to-end: real `200`s, real product-search payloads reaching Elasticsearch. Also pointed `omfwd` directly at ELK's Tailscale IP (`100.99.54.59:5517`) instead of relaying through pfSense's DMZ gateway (`172.16.0.2`) — same "skip the unnecessary hop" reasoning as today's Suricata→Redis change, since this VM already has its own Tailscale identity.

**Open issue — not yet root-caused**: every HTTP access log line is landing in Elasticsearch **3 times** (confirmed with a uniquely-tagged test request: exactly 1 line in the source Docker json-log, exactly 3 docs in ES). Ruled out so far: nginx itself (only 1 line per request in its own container log), multiple rsyslogd processes/duplicate config blocks (only one clean instance/config found), and pfSense as a relay cause (still tripled after bypassing pfSense and sending straight to ELK). Likely culprit is rsyslog's `omfwd`/action-queue retry behavior or something on Logstash's `tcp`/5517 input side — not yet dug into further. Doesn't break delivery, just inflates counts/volume in dashboards. **Pick this up first next session.**
