# Session 15 — 2026-08-06

## Two bugs found in `soc-logs-*`, one real, one self-inflicted

`soc-logs-*` (pfSense filterlog) was empty in Kibana. Two separate problems.

### Bug 1 (REAL): pfSense syslogd not forwarding

**Symptom:** `soc-logs-*` empty for ~2 days. Clicking Save on
Status → System Logs → Settings restored it, but only for ~3 minutes.

**What was NOT wrong** (ruled out in this order):

| Checked | Result |
|---|---|
| `filterlog` process | running, PID 91194, since 00:59 |
| `config.xml` `<syslog>` block | correct, `<remoteserver>100.99.54.59:5514</remoteserver>` |
| `/var/etc/syslog.d/pfSense.conf` line 30 | correct, `*.* @100.99.54.59:5514` |
| Route to ELK | correct, via `tailscale0` |
| `/var` as RAM disk | no — only `/var/run` is tmpfs |
| Reboot | no — uptime 9:51, booted 00:58 |

**Root cause:** syslogd had the config loaded (it was writing
`/var/log/filter.log` from line 29 of the *same rule block*) but was not
transmitting to the remote target on line 30. It had failed to establish the
remote destination at startup — almost certainly because `tailscale0` was not
up yet when syslogd started at boot.

**Proof it was a forwarding fault, not a "no events" situation:**

```
tcpdump -ni pflog0              -> 2 packets   (events ARE generated)
tcpdump -ni tailscale0 port 5514 -> 0 packets   (nothing forwarded)
```

**Fix:**

```sh
/usr/local/sbin/pfSsh.php playback svc restart syslogd
```

**WARNING — do not use `killall -HUP syslogd` on this build.** I tried it; it
*terminated* syslogd rather than reloading it (Capsicum/casper). Logging was
fully down until restarted properly. Use the `pfSsh.php` service restart.

**Verified after fix:**

```
10:57:34 IP 100.70.145.65.514 > 100.99.54.59.5514: SYSLOG local0.info, length: 152
```
→ 14 docs in ES, 0 `_grokparsefailure`, all fields parsed
(`src_ip`, `dst_ip`, `action=block`, `protocol=udp`, ports, `real_interface=em0`).

### Debugging trap worth remembering

A `logger -p local0.info 'test'` probe produced **zero** packets and looked like
proof of a broken daemon. It was not. `/var/etc/syslog.d/pfSense.conf` line 28 is
`!filterlog`, and the remote line 30 sits **inside** that block — so *only*
`filterlog` messages are forwarded. A probe with any other tag is correctly
dropped. **Test a scoped syslog path with a message that matches the scope**,
or read the `!program` filters first.

### Bug 2 (SELF-INFLICTED): grok field renamed during bisection

While bisecting Bug 1 I progressively simplified the grok pattern on line 33 of
`logstash.conf` and left the capture named `rest` instead of `filterlog_data`.
Lines 34–41 (the `if [filterlog_data]` guard and the 29-column CSV split) key off
`filterlog_data`, so the CSV split silently never ran.

Restored to `filterlog_data`. Confirmed against the config mirror that the
**original pattern was correct all along** — same single backslashes, no `^`
anchor. My "anchor" and "double-backslash escaping" theories were both wrong.

`_simulate` is the authoritative way to test a grok pattern:

```sh
POST localhost:9200/_ingest/pipeline/_simulate
```

### The lab-is-intermittent problem

Measurement showed 39–62 **empty hours** per source over 7 days — the lab VMs
are only on during work sessions. A naive flatline fires every night and weekend.

Handled with:
- `limit_execution: "* 8-19 * * *"` — cron-gated, only evaluates during lab hours.
- `realert: 6–12 h` — one alert per outage, not one per interval.

#### Trap: `limit_execution` interval crons never fire

I first wrote `"*/10 8-19 * * *"`. The rules loaded, validated, and logged
*"Pausing watchdog_pfsense_filterlog until next run at 10:10 UTC"* — and then
**never executed once**. They were absent from `elastalert_status` entirely.

Cause (`elastalert.py:1242-1256`): `croniter(expr)` is evaluated from *now*, so
`next()` always returns a slot ~10 min ahead. The pause test
`endtime + run_every < exec_next - 59` is therefore always true, the rule
re-pauses, and since `has_run_once` is still `False` (init at line 999) it
`return`s **before** ever running. `has_run_once` is only set *after* that block,
so it never becomes True. Infinite pause loop.

**Rule: the cron must match every minute of the active range (`"* 8-19 * * *"`),
not an interval.** Then during lab hours the next slot is only 60 s away, the
pause test is false, and the rule runs every `run_every`; outside the range the
next slot is hours away, so it correctly pauses.

Verified after the fix — all 5 present in `elastalert_status`.
- Severity 1 and `type: pipeline-health`, tagged `watchdog` — kept out of the
  security alert stream so ops noise never masks a real detection.

Juice Shop is explicitly **advisory**: it only logs when someone touches it, so
silence is genuinely ambiguous. Said so in the rule description rather than
pretending it's a hard signal.

### Result: the full chain works, including the refusal

Alert `~122888288` (Tailscale-sourced XSS on Juice Shop), case `~123113560`:

```
triage   182.4s  -> not FP, high, 0.85, T1190
promote  -> case ~123113560
enrich   -> 6/6 Cortex jobs Success (AbuseIPDB, URLhaus, VirusTotal x2 observables)
verdict  265.0s  -> MALICIOUS, confidence 0.95
guard    -> CONTAINMENT REFUSED: Tailscale CGNAT range
total    514.4s, no unhandled exception
```

The model said malicious at 0.95 — **above** the 0.75 action threshold — and the
deterministic guard refused anyway. That is C-2 in all but the screenshot.

### Four defects found and fixed

| # | Defect | Impact | Fix |
|---|---|---|---|
| 1 | `api.alert.update(id, status=...)` is thehive4py 1.x syntax | FP alerts never marked Ignored; re-triaged forever at ~3 min each | `fields={"status": "Ignored"}`. Verified `New -> Ignored` |
| 2 | `audit("alert_dismissed")` fired *before* the update | audit trail claimed a dismissal that never happened | moved inside `try`; added `alert_dismiss_failed` |
| 3 | `find_observables()` called immediately after `promote_to_case()` | observables not yet indexed -> 0 found -> enrichment, verdict **and containment silently skipped**; run looks "successful" having tested nothing | retry 5x/2s (`OBSERVABLE_FETCH_ATTEMPTS`). 0 reports -> 6 |
| 4 | No filter on alert type | would promote A-1 watchdog alerts into security cases, ~6 min LLM each, 0 observables | `is_operational_alert()` skips `pipeline-health` / `watchdog` |

Also raised `OLLAMA_TIMEOUT` 180 -> 420. A warm triage measured **177.6s** against a
180s timeout — 2.4s from a spurious failure — and `deployment-latency.md` records a
202.8s worst case. The default sat *below* our own measured worst case.

### Quality defect: the model hallucinated its enrichment reasoning

In case `~123113560` the comment says:

> **Reason:** detected as malicious by multiple engines including MalwareURL,
> Phishtank, and Sucuri SiteCheck
> **Key evidence:** MalwareURL: **clean** … Phishtank: **clean** … Sucuri: **clean**

Every engine returned *clean*; the model asserted the opposite and *raised*
confidence 0.85 -> 0.95 on it. The verdict is defensible for an XSS attempt, but the
stated reason is fabricated and contradicted by the evidence in the same comment.

Good argument for the report: **this is why the guard is deterministic and code-side.**
The reasoning was wrong; the refusal was still correct. Worth a slide.
