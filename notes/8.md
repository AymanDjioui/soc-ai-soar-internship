### 2. Juice Shop HTTP log pipeline — root cause finally found and fixed

**Starting point**: yesterday's session ended with the Juice Shop `nginx-proxy` Docker network bug fixed, but a 3x log-duplication issue left open. Picking that up today revealed something much bigger: **the Juice Shop app was completely unreachable via its real access path** (`http://100.70.145.65:8080` — the Tailscale → pfSense NAT → DMZ path that Suricata actually needs to see for detection).

**The (long) troubleshooting path**:
- Confirmed via packet capture on pfSense's `tailscale0` interface: SYN packets to port 8080 never arrived at all — not blocked, not refused, just never delivered. Meanwhile SSH (22) to the same pfSense host over the same tunnel worked perfectly every time.
- Ruled out, in order: the NAT/rdr rule (present, correct), the pf filter rule (present, correct), the Tailscale tailnet ACL (checked in admin console — wide open, "all ports and protocols"), the Juice Shop backend itself (healthy, 200 OK when reached directly).
- **Found and fixed a real, separate bug along the way**: the NAT-associated pf filter rule was missing `sloppy state` (state type), unlike the working catch-all Tailscale rule which had it. Without it, pf matched packets but never created connection state. Patched `config.xml` directly (`<statetype><![CDATA[sloppy state]]></statetype>`), verified it survived a reboot. Legitimate fix, kept — but not the actual root cause of the outage.
- **Caused two real incidents in the process**: an interrupted `rc.filter_configure` (SSH timeout killed it mid-run) and a `tailscaled` restart both left pfSense fully unreachable (SSH + GUI down, only Tailscale ping alive) — needed Badr to reboot the VM via VMware console **twice** to recover. Config on disk was never at risk (only live/runtime state), but this ate a lot of time and is a lesson in being much more conservative about live firewall reloads over an SSH session that can itself get cut.
- Tested a fresh port-forward rule (8081) on a fresh, unused port — failed identically, ruling out "port 8080 specifically is poisoned."
- Both you and Badr independently tested `100.70.145.65:8080` from your own machines and got nothing — ruled out a client-specific/peer-connection issue.
- **The actual root cause**: Badr had added Tailscale directly onto the Alpine/Juice-Shop VM itself (`172.16.0.10`, now also `100.78.58.45` on the tailnet) earlier, just so he could SSH into it. Once that VM was **dual-homed** — reachable both as pfSense's NAT target *and* as its own native tailnet peer — something in Tailscale's mesh routing got ambiguous about how to reach it, and silently black-holed the one path that required pfSense to *relay* traffic onward (the NAT-forward), while direct connections (SSH to pfSense, ping, Redis) stayed completely unaffected.
- **Fix**: Badr ran `tailscale down` on the Alpine VM (from its own console, since SSH to it over Tailscale had also gone flaky). **Immediately fixed** — `http://100.70.145.65:8080/` went from 100% timeout to consistent `HTTP 200` in ~15-20ms, confirmed across multiple repeated tests.

**Trade-off now in place**: Badr lost SSH access to Alpine over Tailscale (that was the only reason it was added). He still has VMware console access as a fallback. If he needs remote SSH again, the clean fix is a dedicated pfSense port-forward for port 22 → `172.16.0.10:22`, same pattern as the working 8080 rule — not done yet, deliberately deferred.

### 3. Juice Shop log parsing bug found (separate from the above)

While investigating the original log-duplication complaint, found that the `juiceshop-docker` Logstash filter had been **rewritten** (by Badr, presumably while also working on the pipeline) to expect classic syslog framing (`<PRI>TIMESTAMP HOST ...` via a `grok` pattern), but the actual rsyslog config on Alpine sends **bare JSON with no syslog prefix** (the `rawJSON` template set up in yesterday's Redis-migration work: just `%msg%\n`). The grok never matched, so the entire parse chain silently failed — logs were landing in Elasticsearch as an unparsed blob under a generic `event.original` field, with `@timestamp` showing ingest time instead of the real event time (a 16-hour-old backlog dump surfaced this clearly).

**Fix applied**: patched `~/elk-stack/logstash/pipeline/logstash.conf` on the ELK VM — removed the syslog `grok` step, parse `message` directly as JSON (`json { source => "message" target => "docker" }` → `json { source => "[docker][log]" target => "access_log" }`), keeping Badr's intended `access_log.*` field naming. Config change is correct and backed up (`logstash.conf.bak.<timestamp>`), but **not yet verified live** — see below.

## 🎤 Report angles unlocked today

- **"Root-caused a subtle distributed-systems bug"**: a device being simultaneously a NAT target *and* a native mesh-VPN peer created a routing ambiguity that silently broke one specific path while leaving everything else looking healthy — a genuinely interesting finding about how overlay networks (Tailscale) and traditional NAT/firewall rules (pfSense) can conflict in non-obvious ways.
- **"Operational discipline under a real incident"**: caused two real outages via interrupted remote firewall reloads, recovered both safely (config-on-disk was never at risk), and adjusted approach afterward (detached/nohup'd commands, GUI-based changes preferred over further blind CLI attempts) — a fair story about incident response, not just the fix itself.
- **"Configuration drift across two contributors"**: the log-parsing break happened because two people (Badr and earlier work) both touched the same pipeline config with different assumptions about the data format — a real, relatable lesson about coordination on shared infrastructure, worth a sentence in any report about process/collaboration.
