## ✅ What was accomplished

### 1. Fixed a stale Kibana data view — root cause of "Discover shows nothing"

The `juiceshop` data view in Kibana was hardcoded to a single historical index (`juiceshop-docker-2026.07.16`) instead of a wildcard pattern. Any time range after that date showed zero results, even though data was flowing correctly. Fixed via the Data Views API — changed `title` to `juiceshop-docker-*`. This was a leftover from whenever the data view was first created, before daily index rotation was accounted for.

### 2. Confirmed the long-standing 3x log duplication issue is gone

Sent a uniquely-tagged test request and got exactly 1 document back, not 3. Likely resolved as a side effect of the full Logstash container recreation + socat relay rebuild earlier in the day (probable original cause: rsyslog `omfwd` retry/queue behavior against a flaky target — a clean restart of the whole chain reset that state). Closes an issue that had been open across three separate sessions.

### 3. Built the Kibana dashboard: "Juice Shop - Traffic & Security Overview"

Built via the Kibana Saved Objects API (classic agg-based visualizations, not Lens — simpler JSON schema to construct directly). Final panel set (8 panels):

- **Requests Over Time** — general traffic volume
- **Status Code Breakdown** — pie chart
- **Top Request URIs** — table
- **Top Client IPs** — table
- **Error Responses Over Time (4xx/5xx)** — filtered histogram
- **Top User Agents** — originally raw UA strings (unreadable, truncated), replaced with a Kibana **runtime field** (`ua_category`, Painless script) that buckets into `Browser` / `curl` / `Wget` / `Nmap Scripting Engine` / `sqlmap` / `python-requests` / `Other/Automated` — much more actionable at a glance
- **Failed Login Attempts Over Time** — added specifically to catch brute-force by *behavior* (rate of failed `/rest/user/login` POSTs), since payload-keyword matching can't catch this attack shape
- **Suspicious Request Events** — a raw saved-search panel (not aggregated), showing individual matching events with client IP, method, URI, status, user agent. Originally URI-only; extended to also match `access_log.request_body` (see #4 below) after realizing body-based payloads were invisible

### 4. Found and fixed a real detection gap: POST body payloads were invisible to logging

While testing a SQLi authentication-bypass scenario (payload in a JSON POST body, not the URL), realized nginx's access log format only ever captured the URI — request bodies were never logged. This meant **any attack sent via POST body content would succeed and be completely invisible to the dashboard**, which would have looked like a false negative rather than what it actually was: a logging gap.

**Fix**: added `"request_body":"$request_body"` to nginx's `log_format` on the Alpine box, restarted `nginx-proxy` to apply, verified the field flows through to Elasticsearch. Then extended the *Suspicious Request Events* search to check both `request_uri` and `request_body` for attack-indicator strings.

### 5. Ran and validated 7 attack scenarios end-to-end, live

Combination of the original 4 (re-verified still working — network/Suricata-level) and 3 new ones (app-level, only visible via the Juice Shop dashboard):

**Already-known, Suricata/IDS-level** (re-confirmed working):
1. Port scan (Nmap) — SID/signature match, geolocation, full IDS dashboard
2. XSS — SID 2009714
3. SQLi (sqlmap-style) — 8 distinct signatures
4. Known-bad-traffic baseline (testmyids.com via pfSense shell)

**New, app-level only** (none of these produce a Suricata signature match — valid HTTP, no payload pattern IDS rules would catch):
5. **Brute-force login** — 5 failed attempts, caught via the new *Failed Login Attempts* behavioral panel
6. **SQL injection authentication bypass** — `' OR 1=1--` in the login POST body. This is the strongest single result of the day: it **actually succeeded**, returning a valid JWT for `admin@juice-sh.op` with `role: admin` — full account takeover with zero real credentials. Caught by the newly-extended *Suspicious Request Events* panel (visible in `access_log.request_body`).
7. **IDOR** — used the stolen admin token from #6 to pull basket #2's contents (`UserId: 2`) while authenticated as user #1. Confirmed genuine unauthorized cross-user data access, not just a probe. Visible in *Top Request URIs* as a tight sequential `/rest/basket/1` through `/rest/basket/5` cluster.

**Tested but ruled out** (documented honestly rather than omitted):
- Path traversal (`/ftp/../../../../etc/passwd`) — nginx/Juice Shop normalized the path and served the SPA shell instead of leaking file content. A real result worth keeping in the report: shows what was tried and didn't work, not just successes.

### 6. Built a reusable live-demo runbook

`demo/attack-scenarios.md` — copy-paste-ready commands for all core scenarios plus notes on what to look for in Kibana for each, specifically so a future live demo (e.g. for the external encadrant) is just "paste command → point at dashboard," no improvisation needed.

### 7. Organized all screenshot evidence by detection layer, not chronology

Verified every existing screenshot's actual on-screen content (not just filename) before sorting, into:

- **`screenshots/detected-by-firewall-ids/`** — the 4 original scenarios, all showing the Suricata "IDS Detections Dashboard"
- **`screenshots/detected-by-juiceshop-app/`** — the 3 new scenarios, all showing the Juice Shop app dashboard

This split is itself a useful report narrative: it makes visible *why* both detection layers matter — network IDS catches signature/payload-based attacks, but business-logic attacks (brute force, IDOR, auth bypass) are only visible through application-level logging. Neither layer alone would have caught everything demonstrated today.

## ⚠️ Known issues / follow-ups

1. **The socat relay (from earlier today) has no monitoring** — still true, carried over from notes/9.md. Worth an ElastAlert rule watching for "no juiceshop-docker documents in N minutes."
2. **Suricata has no rules for the new app-level attack classes** — brute force, IDOR, and body-based SQLi are, by design, invisible to network IDS. This isn't a gap to "fix" so much as the actual justification for the dual-layer architecture — worth stating explicitly in the report rather than treating as unfinished work.
3. Still pending from earlier sessions: Suricata on LAN (`em1`), Windows VM, Alpine SSH access restoration.
4. Consider whether `request_body` logging should be size-limited or redacted for fields like passwords in a more production-like setup — logging raw POST bodies indefinitely (including credentials attempted during brute-force testing) is a deliberate lab-only tradeoff, worth one sentence of acknowledgment in the report.

## 🎤 Report angles unlocked today

- **"Full account takeover via SQL injection, not just an error message"**: most SQLi demos stop at "the app returned a 500" — this one returned a working admin JWT, a much stronger and more concrete finding.
- **"Why detection needs two layers, demonstrated not just claimed"**: the firewall-ids vs juiceshop-app screenshot split is direct, visual proof that network IDS and application logging catch genuinely different attack classes — a stronger argument than describing it in prose.
- **"Found a logging blind spot before it caused a false negative"**: catching the POST-body gap *while testing*, before it silently swallowed a real attack, is a good example of validating your own detection pipeline rather than trusting it blindly.
- **"Documented a negative result on purpose"**: keeping the failed path-traversal attempt in the evidence set, rather than only showing successes, is a small but real credibility signal for the report.
