## 🐛 First run: traffic reached em1, but zero alerts — found a real gap

First pass produced `dns`/`http`/`tls` events correctly tagged `in_iface: em1` from both
hosts (proof traffic crosses the interface) but **no `event_type: alert` at all** — the
actual signature match landed on `em0` (WAN) instead, on the NAT'd post-translation IP.
Checked the full `suricata-alerts-*` index history: **zero `event_type: alert` documents
had ever been tagged `em1`**, not just in this test window.

**Root cause** (found via direct SSH to pfSense, comparing the three instance
directories under `/usr/local/etc/suricata/`):

| Interface | Instance dir | Compiled ruleset size |
|---|---|---|
| `em0` (WAN) | `suricata_31165_em0` | 22,622 lines |
| `em2` (DMZ) | `suricata_40069_em2` | 51,051 lines |
| `em1` (LAN) | `suricata_26152_em1` | **389 lines** |

`em1`'s `suricata.rules` contained *only* Suricata's built-in decoder/protocol-anomaly
rules (`sid:22xxxxx`/`2200000`-range — "Applayer Mismatch protocol", "TLS certificate
invalid X", etc.), zero ET/GPL content-signature categories. This explains everything:
capture worked fine (hence flow/protocol metadata logging), but there was no actual
signature to match against, so `alert` events were structurally impossible on this
interface. Despite notes/11.md recording "Categories → Select All, matching DMZ" during
the `em1` setup on 2026-07-24, that selection evidently never got compiled into the
live ruleset — a real, silent rules-sync gap specific to that one interface, undetected
until this test because nobody had checked for a genuine signature match before.

## ✅ Fixed a third, smaller issue: GeoIP "Missing Value" for internal traffic

Noticed in a TheHive alert screenshot: `Country: <MISSING VALUE>` on a LAN-sourced
alert. Root-caused via the raw ES doc — `geoip_src: {}`, tagged `_geoip_lookup_failure`.
Not a bug: MaxMind's GeoLite2-City database has no entries for private/RFC1918 address
space (`192.168.10.0/24` is private), so the lookup correctly fails for internal IPs —
it just wasn't visible before because WAN/DMZ alerts almost always had a real public
source IP. Now that LAN (`em1`) is live, most of its traffic is private-to-private, so
this shows up constantly.

**Fix**: added a `cidr` filter + conditional `mutate` right after each existing `geoip`
filter pair, in both the pfSense/filterlog block and the `suricata_eve` block of
`logstash.conf` — checks `src_ip`/`dest_ip` against RFC1918 ranges *and* Tailscale's
CGNAT range (`100.64.0.0/10`, also un-geolocatable), and sets
`geoip_src.geo.country_name` / `geoip_dst.geo.country_name` to `"Internal (LAN)"` when
so. Validated config with `logstash -t` before restarting (clean), then confirmed two
real cases post-restart: a public→LAN alert now correctly shows `Germany` on the
source side and `Internal (LAN)` on the destination side (previously the dest side
alone would've been missing); a LAN→LAN alert (the SSDP one) shows `Internal (LAN)` on
both sides. Backed up the pre-edit config to
`~/elk-stack/logstash/logstash.conf.bak-20260728-geoip` (outside the pipeline directory,
per the dup-processing lesson from notes/11.md) before editing.

## ✅ Fixed the Juice Shop DMZ log pipeline — three stacked bugs, all found via direct SSH access

Badr brought the Juice Shop VM back up (it had been down, `juice-shop-app`'s old Tailscale
identity permanently offline since it was uninstalled per notes/9.md — no VPN on this VM,
confirmed with the user). App itself came back fine (`curl` through the NAT path → 200),
but `juiceshop-docker-*` hadn't seen a real document since **2026-07-24**, 4 days of
silence despite the app answering requests correctly.

Got direct SSH access to the VM for the first time this session (root@172.16.0.10, no
VPN — reached via **pfSense as an SSH jump host**, `ssh -J admin@100.70.145.65
root@172.16.0.10`, since pfSense routes the DMZ directly but my own machine has no route
into `172.16.0.0/16`). Found three separate, stacked problems, each masking the next:

1. **Missing firewall rule (the actual root cause)**. `netstat` on the DMZ VM showed
   rsyslog's connection to the relay stuck in `SYN_SENT` forever — TCP handshake never
   completing. Diffed every rule on the DMZ (`opt1`) interface in `config.xml`: only two
   existed (LAN→DMZ pass, DMZ→LAN block) — **nothing allowing DMZ-sourced traffic to
   reach pfSense itself on port 5517**, so packets were silently dropped by the default
   deny. Someone (Badr) had built the receiving side properly — a native `syslog-ng`
   "Remote Logging" listener (`source juiceshop_src { network(ip("172.16.0.2")
   port(5517)...) }`, superseding the old ad-hoc `socat_juiceshop.sh` script from
   notes/9.md, which is still enabled in `rc.conf.local` but no longer running since
   syslog-ng holds the port first at boot) — but never added the matching firewall pass
   rule, unlike the equivalent Redis/Suricata rule on the Tailscale interface which has
   both pieces. **Fixed** by writing a small PHP script using pfSense's own config API
   (`require_once("config.inc"); ... $config['filter']['rule'][] = ...; write_config();
   filter_configure();`) run via `php -f` — not a raw XML edit, mirrors exactly what the
   GUI's Save button would do, avoiding the class of outage two raw-XML edits caused
   earlier in this project. Backed up `config.xml` first. Verified: manual `nc` from the
   DMZ VM to the relay went from hanging to instant success, connection state went
   `SYN_SENT` → `ESTABLISHED`.
2. **Stale `imfile` watch**. Even after the firewall fix, real HTTP traffic wasn't
   landing — confirmed the request WAS written to nginx-proxy's actual Docker JSON log
   file (`grep` found it), but rsyslog's `imfile` state files hadn't advanced since
   before the VM's suspend/resume. `rc-service rsyslog restart` cleared it — document
   count in Elasticsearch immediately started climbing as it caught up on the backlog.
3. **Format mismatch introduced by the newer relay**. The old `socat` relay was a dumb
   byte-for-byte TCP proxy — zero reformatting. The new `syslog-ng` relay wraps every
   forwarded message in its own syslog envelope (`<13>Jul 28 ... 172.16.0.10 {...json...}`)
   by default, which Logstash's `json` filter can't parse directly (same silent-failure
   shape as the original bug in notes/8.md, different cause). **Fixed** in
   `logstash.conf`'s `juiceshop-docker` filter: added an optional `grok` that strips a
   leading syslog envelope if present (`^<%{POSINT}>%{SYSLOGTIMESTAMP} %{IPORHOST}
   %{GREEDYDATA:json_payload}$`), replacing `message` with the unwrapped payload before
   the existing `json` filter runs — tolerant of either relay, doesn't require picking a
   side on socat-vs-syslog-ng. Validated with `logstash -t` before restarting.

**Bonus, non-blocking finding**: the DMZ VM's clock was drifted ~4 days behind (same
VM-suspend pattern as before). Tried `ntpd -q` to fix it properly — discovered the DMZ
interface has **zero outbound internet access at all** (ping, HTTP, DNS all fail; only
two rules exist on that interface, neither permits general egress). This is correct,
intentional DMZ isolation, not a bug — didn't touch it. Just manually set the correct
time (`date -u -s`) as a stopgap; a real fix would mean pointing the VM's NTP at
pfSense's own local time service instead of the public internet, which needs one more
narrow firewall rule — flagged for the user to decide, not done unprompted.

**Full end-to-end verification**: a uniquely-tagged fresh request now lands in the
*correct, current-dated* index (`juiceshop-docker-2026.07.28`) with fully parsed
`access_log.*` fields (`request_uri`, `status`, `method`, etc.) within seconds.
