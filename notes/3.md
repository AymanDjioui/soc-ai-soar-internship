### 2.4 Architectural decisions worth reporting

**Bridged → NAT → Tailscale progression.** Initial plan called for bridged networking between the two lab machines. On WiFi-hosted VMware installs this is broadly unsupported (driver promiscuous mode limitations). Fallback was NAT + explicit `vmnet8` port forwarding (`/etc/vmware/vmnet8/nat/nat.conf`). Final architecture uses Tailscale-inside-the-VMs, which sidesteps host-level networking entirely and gives each VM a stable overlay identity. **This is a legitimate report narrative — "architectural constraint, workaround, and clean solution."**

**Two Kibana data views, not one — intentional.**

- `soc-logs-*` → pf firewall connection telemetry (allow/block per rule)
- `suricata-alerts-*` → IDS signature matches These are conceptually different data types (connection logs vs detection alerts). Keeping them separate is standard SOC practice and mirrors how a real SIEM handles multi-source ingestion.

**TCP + `json_lines` for Suricata, not UDP.** Suricata EVE JSON alerts include full HTTP context (base64 payloads, packet dumps) which routinely exceeds UDP packet boundaries. Initial UDP delivery caused JSON events to fragment across packets, and Logstash's `json` filter would only parse the first fragment — most alerts landed in `event.original` as garbled blobs. Switching to TCP with the `json_lines` codec fixed this instantly.

**Filebeat considered, deferred.** The "correct" delivery method is Filebeat on PfSense. PfSense's FreeBSD 15 base has no prebuilt Filebeat binary; all existing `pfsense-filebeat` projects target FreeBSD 11 or 12 and are ABI-incompatible. Compiling from Go source is feasible but ~30-60 minutes on constrained VM resources. TCP + `nc` was chosen as a lab-appropriate substitute; Filebeat compilation is documented as a next-iteration improvement.

### 3.4 Logstash pipeline

`~/elk-stack/logstash/pipeline/logstash.conf`:

```
input {
  beats { port => 5044 }
  udp   { port => 5514 ; type => "syslog" }
  udp   { port => 5515 ; type => "suricata_eve" }
  tcp   { port => 5516 ; codec => json_lines ; type => "suricata_eve" }
}

filter {
  if [type] == "syslog" {
    grok {
      match => { "message" => "<%{POSINT:syslog_pri}>%{SYSLOGTIMESTAMP:syslog_timestamp} filterlog\[%{POSINT:syslog_pid}\]: %{GREEDYDATA:filterlog_data}" }
    }
    if [filterlog_data] {
      csv {
        source => "filterlog_data"
        separator => ","
        columns => ["rule_number","sub_rule_number","anchor","tracker_id","real_interface",
                    "reason","action","direction","ip_version","tos","ecn","ttl","ip_id",
                    "offset","flags","proto_id","protocol","length","src_ip","dst_ip",
                    "src_port","dst_port","data_length","tcp_flags","sequence_number",
                    "ack_number","window","urgent","options"]
      }
      mutate {
        convert => {
          "ttl" => "integer"
          "src_port" => "integer"
          "dst_port" => "integer"
          "length" => "integer"
        }
        remove_field => ["message", "filterlog_data"]
      }
    }
  }

  if [type] == "suricata_eve" {
    json { source => "message" }
    mutate { remove_field => ["message"] }
  }
}

output {
  if [type] == "suricata_eve" {
    elasticsearch {
      hosts => ["http://elasticsearch:9200"]
      user => "elastic"
      password => "${ELASTIC_PASSWORD}"
      index => "suricata-alerts-%{+YYYY.MM.dd}"
    }
  } else {
    elasticsearch {
      hosts => ["http://elasticsearch:9200"]
      user => "elastic"
      password => "${ELASTIC_PASSWORD}"
      index => "soc-logs-%{+YYYY.MM.dd}"
    }
  }
  stdout { codec => rubydebug }
}
```

### 3.5 pf filterlog format reference (for report)

Raw line example:

```
<134>Jul  3 13:35:31 filterlog[899]: 4,,,1000000103,em1,match,block,in,4,0x10,,128,0,0,none,17,udp,328,0.0.0.0,255.255.255.255,68,67,308
```

**Syslog envelope decoded:**

- `<134>` → PRI byte: facility 16 (`local0`), severity 6 (`info`) → `local0.info`
- `Jul 3 13:35:31` → generation timestamp
- `filterlog[899]` → FreeBSD daemon name + PID

**CSV payload field-by-field (TCP/UDP over IPv4):**

|#|Field|Sample|Meaning|
|---|---|---|---|
|1|`rule_number`|`4`|Position in ruleset — **NOT stable across rule edits**|
|4|`tracker_id`|`1000000103`|Unique rule ID — **stable**, use for correlation|
|5|`real_interface`|`em1`|NIC that saw the packet|
|6|`reason`|`match`|Why rule fired|
|7|`action`|`block` / `pass`|Firewall decision|
|8|`direction`|`in` / `out`|Relative to interface|
|9|`ip_version`|`4` / `6`|IPv4 or IPv6|
|17|`protocol`|`tcp`, `udp`, `icmp`|L4 protocol name|
|19|`src_ip`|`192.168.84.134`|Source address|
|20|`dst_ip`|`239.255.255.250`|Destination address|
|21|`src_port`|`43037`|Source port (TCP/UDP only)|
|22|`dst_port`|`1900`|Destination port|

**Important quirks discovered:**

- Field count differs by protocol: UDP is shorter than TCP (no `tcp_flags`, `sequence_number`, `ack_number`, `window`, `urgent`, `options`). CSV filter fills missing columns with `nil` — harmless for UDP.
- **ICMP layout is different** (has `icmp_type`/`icmp_code` instead of ports). Current filter will misalign ICMP entries — flagged for later fix.
- `1000000103` is pfSense's **implicit default deny rule** on WAN. Auto-logs out of the box; most of the WAN traffic captured was internet scan noise correctly being blocked.

5. On the WAN interface's **Categories** tab, enable at minimum:

    - `emerging-exploit`
    - `emerging-web_server`
    - `emerging-malware` (note: `emerging-trojan` does NOT exist — trojans live in emerging-malware)
    - `emerging-attack_response` (this is what caught the testmyids.com test)
    - `emerging-policy` (optional)

### 4.3 EVE JSON output configuration (per interface)

`Services → Suricata → Interfaces → WAN Settings → EVE Output Settings`:

- **EVE JSON Log:** ✅
- **EVE Output Type:** `FILE`
- **EVE Log Alerts:** ✅
- Extended options (HTTP/DNS/DHCP/etc.) enabled by default — useful for later scenarios but noisy on WAN

Restart the Suricata interface (⏸ then ▶) for changes to take effect.

**Resulting file location:** `/var/log/suricata/suricata_em0<ID>/eve.json` (folder ID changes across restarts; use `find /var/log/suricata -name eve.json` to locate).

### 4.4 Hardware offloading — critical Suricata prerequisite

`System → Advanced → Networking`, check all three:

- ☑ Disable hardware checksum offload
- ☑ Disable hardware TCP segmentation offload
- ☑ Disable hardware large receive offload

**Why:** If NIC hardware does checksum/segmentation before Suricata sees the packet, Suricata can misread packet boundaries and miss detections. Confirmed on the WAN Interface Settings page via yellow warning banner that persists until fixed. **Requires reboot to apply on VMware `em` (Intel e1000 emulation) NICs.**

### 4.5 Delivery to Logstash — TCP + json_lines

**Why not UDP:** Full Suricata alerts include large HTTP payloads and base64 packet dumps (~2-5 KB per alert). These exceed UDP MTU and get fragmented; Logstash's `json` filter only parses the first fragment, so alert events landed as garbled blobs in `event.original`.

**Solution:** TCP delivery with the `json_lines` codec (see pipeline config in section 3.4). Each newline-terminated JSON object is treated as one complete event, and TCP handles ordering.

**Forwarder command (run on PfSense):**

```
nohup sh -c 'tail -F /var/log/suricata/suricata_em0<ID>/eve.json | nc 100.99.54.59 5516' >& /tmp/eve_forward_tcp.log &
```

Note: `tcsh` syntax uses `>&` for stdout+stderr redirection (not bash's `2>&1`).

**Known limitation:** does not survive PfSense reboot. Would need a rc.d startup script for persistence — deferred.

## 5. Troubleshooting Playbook (issues encountered & resolved)

Kept as a checklist so the same fixes are reusable in the report and by teammates.

### 5.1 Environment / infrastructure

- **VMware kernel modules unsigned after Ubuntu kernel auto-update (Secure Boot host).** Solution: sign `vmmon` / `vmnet` with enrolled MOK key. **Do NOT** re-run `vmware-modconfig --install-all` afterwards — it rebuilds unsigned modules and invalidates the signing.
- **Docker volume mount created `logstash.yml` as a directory.** Solution: ensure config files exist before `docker compose up`; Docker auto-creates missing files as directories.
- **`logstash.yml` mount with `:ro` flag crashed Logstash.** Entrypoint requires write access. Mount without `:ro`.
- **`kibana_system` user password not set by `ELASTIC_PASSWORD` env var.** Must be set separately via Elasticsearch API.
- **VMware bridged networking failed on WiFi host** (`wlp1s0` promiscuous mode restriction). Fallback → NAT + `vmnet8` port forwarding. Long-term solved by moving to Tailscale-inside-the-VM.

### 5.2 Logstash config debugging patterns

- **UDP `nc` "success" is not proof of listening.** `nc -uzv` checks reachability, not that anything is bound to the port. Verify with actual traffic + Logstash logs.
- **Docker port mapping is separate from Logstash's internal listener.** Adding a `udp/tcp` block to `logstash.conf` is not enough — also add the `- "PORT:PORT/tcp"` (or `/udp`) mapping to `docker-compose.yml`, and use `docker compose up -d logstash` (not just `restart`) to recreate the container with the new port binding.
- **`docker compose restart` reloads mounted config but does not recreate the container.** For port changes, use `docker compose up -d <service>` or `stop` + `up -d`.
- **Terminal paste corruption on large heredocs.** Large multi-line `cat > FILE << 'EOF'` blocks sometimes get corrupted (bytes reordered, EOF marker mangled). Workaround: use `nano` and paste there instead — nano's input buffer is more resilient.

### 5.3 pfSense-specific

- **Fresh pfSense VM logs nothing until rules have logging enabled.** WAN default deny rule (`tracker_id 1000000103`) auto-logs, but per-rule logging on LAN/OPT1 rules is a per-rule checkbox that starts unchecked. `Firewall → Rules → [rule edit] → Log packets that are handled by this rule`.
- **WebGUI access via LAN/OPT1 does not generate loggable events.** That traffic is handled by the anti-lockout rule, not the loggable interface rule chain. Test with real routed traffic through the firewall.
- **Suricata offloading warning banner won't clear until reboot** on VMware `em` NICs, and even then may need forcing via `ifconfig em0 -rxcsum -txcsum -tso4 -tso6 -lro`.
- **Suricata EVE JSON output disabled by default** — must be enabled per-interface in `EVE Output Settings`.
- **`emerging-trojan` rules category doesn't exist**; trojan detections live under `emerging-malware.rules`.

### 5.4 Delivery-chain pitfalls

- **`tail -F | nc` doesn't survive session close.** Use `nohup ... &` and log to `/tmp/*.log` for later inspection.
- **UDP + large JSON = fragmented events = broken parsing.** Always use TCP for structured multi-line data.
- **`nc` in `tcsh` uses `>&` for combined redirection**, not bash's `2>&1`.

## 9. Key learnings summary

- `tracker_id` is stable, `rule_number` is positional — always correlate rules by tracker_id.
- Suricata offloading warning is not cosmetic — it can silently break detection.
- Structured JSON delivery is a network-protocol question, not just a Logstash question — TCP + newline-delimited framing is table stakes for multi-line records.
- Docker port mapping and container-internal listener bindings are two separate things — both must match.
- Two-data-view Kibana architecture (`soc-logs-*` for connection telemetry, `suricata-alerts-*` for detection alerts) is the correct SOC pattern, not a workaround.
- pfSense's implicit default-deny WAN rule provides continuous no-effort test data — legitimate lab telemetry, not "empty" logs.
- FreeBSD 15 pfSense is currently a difficult target for prebuilt Elastic tooling (Filebeat, etc.) — expect any Beats work to require source compilation.
