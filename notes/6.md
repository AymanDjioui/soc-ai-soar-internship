### 2. ELK → TheHive integration via Elastalert2 — COMPLETE

**Original plan**: Kibana Webhook connector → TheHive API.
**Blocker discovered**: Webhook connector is a Gold license feature. Basic license returns `403 Forbidden: Action type .webhook is disabled`.

**Pivot**: Deployed Elastalert2 as the open-source alternative. This is actually the standard ELK-on-Basic-license SOC pattern and aligns with the encadrant's "including GitHub" scope for benchmarking.

Steps taken:

- Enabled the three Kibana encryption keys required for Alerting (`XPACK_ENCRYPTEDSAVEDOBJECTS_ENCRYPTIONKEY`, `XPACK_SECURITY_ENCRYPTIONKEY`, `XPACK_REPORTING_ENCRYPTIONKEY`) — kept for future use even though we ended up not using Kibana Alerting.
- Added Elastalert2 service to `docker-compose.yml` (image `jertel/elastalert2:2.19.0`).
- Created `~/elk-stack/elastalert/config.yaml` — connects to Elasticsearch on the internal Docker network (`elasticsearch:9200`), runs every minute, 5-minute buffer.
- Created `~/elk-stack/elastalert/rules/suricata_high_severity.yaml` — queries `suricata-alerts-*` for `event_type: alert` AND `alert.severity <= 2`, forwards matches to TheHive.
- Enabled `--verbose` flag on Elastalert command to get INFO-level logs (default WARNING hides the query cycle).

TheHive version detected via `/api/status`: **5.7.1** at `http://100.124.232.121:9000`.

### 3. TheHive alerter with observables — COMPLETE

**Issue**: First working version used `alert: post` (generic HTTP), which can only send flat payloads. Result: alerts arrived in TheHive but with **0 observables** and template placeholders (`{match[alert][signature]}`) rendered literally in the description.

**Fix**: Switched to Elastalert2's native `hivealerter`, which handles TheHive's alert schema natively including observables.

Final rule uses:
- `alert_text` + `alert_text_args` with Python positional formatting for description
- `hive_observable_data_mapping` with bare field names to auto-attach `src_ip` and `dest_ip` as `ip` observables
- `hive_connection` block for auth (Bearer token, `hive_verify: false`)

**Verification**: `curl testmyids.com` from pfSense → TheHive alert appears within 60 seconds with:
- Fully interpolated description (signature, category, severity, source IP, dest IP, country, timestamp)
- 2 observables attached (src_ip = 217.160.0.187/testmyids Germany, dest_ip = 192.168.84.134/pfSense WAN)
- Tags: `elk, elastalert, suricata, auto`
- Severity MEDIUM, TLP/PAP AMBER, source `elk-elastalert`

Also validated E2E from laptop via SSH port-forward tunnel (`ssh -L 9999:testmyids.com:80 admin@100.70.145.65`) — same result, alert #10 in TheHive.

### Key rule file — `suricata_high_severity.yaml`

```yaml
name: Suricata High Severity Alert
type: any
index: suricata-alerts-*

filter:
  - bool:
      must:
        - term:
            event_type: "alert"
        - range:
            alert.severity:
              lte: 2

realert:
  minutes: 5

alert_text_type: alert_text_only
alert_text: |
  Signature: {0}
  Category:  {1}
  Severity:  {2}
  Source IP: {3}
  Dest IP:   {4}
  Country:   {5}
  Time:      {6}
alert_text_args:
  - alert.signature
  - alert.category
  - alert.severity
  - src_ip
  - dest_ip
  - geoip_src.geo.country_name
  - "@timestamp"

alert:
  - hivealerter

hive_connection:
  hive_host: http://100.124.232.121
  hive_port: 9000
  hive_apikey: <ROTATE_ME>
  hive_verify: false

hive_alert_config:
  title: "Suricata alert"
  type: "suricata"
  source: "elk-elastalert"
  severity: 2
  tlp: 2
  pap: 2
  status: "New"
  follow: True
  tags:
    - elk
    - elastalert
    - suricata
    - auto

hive_observable_data_mapping:
  - ip: src_ip
    tags:
      - src
      - suricata
  - ip: dest_ip
    tags:
      - dst
      - suricata
```

### Suricata only sees WAN — internal source IPs not captured

Current architecture: Suricata monitors pfSense's `em0` (WAN). This means:
- Outbound requests: `src_ip` = pfSense WAN post-NAT, real internal source lost
- Inbound attacks: `src_ip` = real external attacker (correct)
- Detection on `curl testmyids.com` shows the testmyids reply, not the initiator

For a proper demo showing internal source attribution, options identified:
- **Option A** (roadmap Priority 6): victim VM behind pfSense + external attack via port forward
- **Option B**: enable Suricata on LAN interface (`em1`) too — 10 min setup
- **Option C**: write a second Elastalert rule on `soc-logs-*` (filterlog data), which already has pre-NAT source IPs

Deferred — will pick one based on encadrant priority.
