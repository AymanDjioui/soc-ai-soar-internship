## Why this needed a different approach than C-1

C-1's "attacker" IP was real and public, so real threat-intel (VirusTotal, AbuseIPDB)
had genuine data on it. C-2 needs the opposite: a target that's one of our own
private/Tailscale addresses. But public threat-intel services have no visibility into
private, non-routable address space by definition — querying them about
`100.99.54.59` can only ever return "no data," never a fabricated malicious signal.
That means a live pipeline run on an internal IP will, correctly and predictably,
produce a `BENIGN` verdict — which never even reaches `containment_allowed()`, since
containment is only attempted when `verdict["verdict"] == "malicious"` (confirmed by
reading the code directly, `e2e_soc_orchestrator.py` ~line 984). So a live-only test
would prove the wrong thing (the AI doesn't get excited about our own infra) rather
than the thing C-2 is actually supposed to prove (the guard overrides a malicious
verdict on a protected target). Ran both, since both are real and useful:

## Part 1 — live pipeline, real Cortex enrichment on an internal IP

Injected a synthetic alert: `src` observable = `100.99.54.59` (our ELK/SIEM server's
Tailscale IP), description written as realistic beaconing-detection language (not

Result, and it's a genuinely interesting one, not just "nothing happened": Phase 1
triage read the described pattern as `medium` severity, not a false positive — a
reasonable, appropriately cautious read of beaconing-shaped traffic. Phase 2
enrichment then checked the real IP against VirusTotal (0/91) and AbuseIPDB (score 0)
and correctly overrode to `BENIGN`, with the system explicitly explaining the
disagreement: *"enrichment assessment is based on more evidence and takes
precedence."* No containment attempted (`reason: "no malicious verdict"`). Case
`~164077816`.

This proves: the system doesn't falsely flag its own infrastructure under real
conditions, and the two-phase disagree-and-defer-to-evidence logic works as designed
— but it doesn't exercise the guard's override behavior, since there was nothing for
the guard to override.

## Part 2 — direct guard test with a synthetic malicious verdict

Same technique already validated for the kill-switch test: call the real
`containment_allowed()` function directly with a manufactured high-confidence
malicious verdict, since that's the only way to honestly test "guard overrides a
malicious verdict on a protected target" given real threat-intel can't organically
produce one. Ran three checks:

| Target | Confidence | Result |
|---|---|---|
| `100.99.54.59` (explicitly in `PROTECTED_ASSETS`) | 0.95 | Refused — `"policy guard: explicitly protected lab asset"` |
| `100.101.27.63` (ordinary lab machine, NOT in the hardcoded list) | 0.92 | Refused — `"policy guard: Tailscale CGNAT range — our own administrative access path"` |
| `68.64.183.127` (C-1's real external threat, sanity check) | 0.92 | **Allowed** — `"all guardrails passed"` |

The second row matters: it proves the protection isn't just a hardcoded IP list — the
general Tailscale/CGNAT range check (`100.64.0.0/10`) catches any of our own
addresses, not only the few explicitly named ones. The third row proves the guard
isn't blanket-conservative — it still correctly allows action against a genuine
external threat at the same confidence level.

Produced real evidence, not just a terminal output: posted a clearly-labeled comment
(`## C-2 GUARD TEST — SYNTHETIC VERDICT INPUT`, explicit note that this is a
manufactured test input, not a live run) to the same case via the orchestrator's own
`build_ai_comment()` / `post_case_comment()`, and wrote a real `containment_refused`
audit log entry via the orchestrator's own `audit()` function (with a `note` field
flagging it as a synthetic-verdict test). Confirmed both landed correctly via the
TheHive API afterward. Confirmed via `pfctl -t EasyRuleBlockHostsWAN -T show` on
