## ✅ Task 1 — Linux LAN host (`192.168.10.20`, Alpine)

### Fixed a real parsing bug
The shared Logstash `syslog` filter only had a grok pattern for pfSense's own
`filterlog[PID]:` format. Any generic Linux syslog line (crond, sshd, su, etc. from the
new host) failed to parse — `_grokparsefailure` tagged, no usable fields. Added a fallback
grok pattern for generic BSD syslog (`<PRI>timestamp program[pid]: message`), applied only
when the pfSense-specific pattern doesn't match (`if ![filterlog_data]`).

### Found and fixed a real duplicate-event bug
While validating the fix, every test event was landing as **2 identical documents**.
Root cause: my own backup file (`logstash.conf.bak.<timestamp>`) had been saved *inside*
`logstash/pipeline/` — the directory Logstash concatenates as a single pipeline when given
a directory path. So every input/filter/output block was defined twice, doubling every
single event platform-wide (not just Linux LAN — this would have silently doubled Suricata
and Juice Shop counts too). Fixed by moving the backup to the parent `logstash/` folder
(where prior sessions' backups correctly lived) and recreating the Logstash container.
Confirmed via clean re-test: 1 packet in → 1 document out, no failure tag.

### Fixed two stale Kibana data views
`linux-lan-logs` and `lan-windows-logs` data views were both hardcoded to a single day's
index (`*-2026.07.20`) instead of a wildcard — same class of bug fixed for Juice Shop
weeks ago, recurring here. Fixed both via the Data Views API.

### Root-caused why SSH events weren't reaching the dashboard
Two separate issues stacked on top of each other:
1. **VM clock frozen at `Jul 16 23:42`** (suspended, not rebooted — same class of bug as
   the Juice Shop VM earlier this project). sshd was logging correctly locally the whole
   time; only the *shipped* copy had a stale embedded timestamp. Fixed with a one-time
   `ntpd -q` sync + persistent OpenRC `ntpd` service, same pattern as before.
2. **Docker's UDP port-publishing doesn't reliably preserve the real source IP.** The
   output routing in Logstash picked the target index by matching `sender_ip` against this
   host's Tailscale IP — but real traffic arrived showing Docker's own bridge gateway
   (`172.18.0.1`) instead, silently falling into the generic `soc-logs-*` catch-all. Fixed
   the durable way: gave the Linux LAN host its **own dedicated UDP port (5518)** instead
   of sharing pfSense's port 5514, and switched routing to key on `type` (authoritative)
   instead of `sender_ip` (fragile). Verified end-to-end: fresh failed-login events now
   land correctly in `linux-lan-logs-*` within seconds.

### Built the dashboard
**"Linux LAN Host - Auth & Activity Overview"** — 6 panels: Events Over Time, Top
Programs, Failed SSH Logins, Successful SSH Logins, Sudo/Privilege Events, and a raw
"Auth & Privilege Events" search (sshd/sudo/su/user-mgmt/cron).

### Validated 3 attack classes end-to-end
1. **SSH brute force** — 5 failed attempts, one triggered the host's own connection-rate
   penalty (`srclimit_penalise`) — a real defensive signal worth citing.
2. **Privilege escalation via `su`** (no `sudo`/`doas` installed on this Alpine image) —
   found a usable detection signal: `syslog_message` is prefixed `+` for a successful `su`
   and `-` for a failed one.
3. **Persistence via cron** — planted a fake reverse-shell cron entry
   (`nc -e /bin/sh <ip> 4444`); its first *execution* showed the full command line in
   `crond`'s log. **Documented gap**: the crontab *edit* itself isn't logged, only its
   *execution* — up to a 1-minute detection lag for an attacker planting persistence.

Cleaned up all test artifacts (cron entry, test user) after.

### Side quest — root-caused Badr's Kibana access problem
Badr reported losing Kibana access after an unrelated ELK stack restart. Diagnosed via a
guided remote diagnostic (`tailscale status`, ping, curl to `/login`, PMTU black-hole
test): Devoteam's corporate network was silently dropping fragmented WireGuard packets —
small requests (`/api/status`) worked, anything requiring a larger response (`/login`'s
full page) hung forever. Confirmed via a binary-search MTU sweep (fails at 1200, succeeds
at 1000). Fix: `sudo ip link set dev tailscale0 mtu 1000` on Badr's machine. Not
persistent across reboots — worth a permanent systemd/udev fix later if it recurs.

## ✅ Task 2 — Windows LAN host (`192.168.10.30`, Windows 10 Enterprise LTSC)

### Got remote execution working
No WinRM initially, RDP-only. Walked the user through enabling it live over RDP:
- `Enable-PSRemoting -Force` initially failed — network category was **Public**, which
  blocks `Set-WSManQuickConfig`'s firewall step by design. Fixed with
  `Set-NetConnectionProfile -NetworkCategory Private`, then re-ran cleanly.
- `Set-Item WSMan:\localhost\Service\Auth\Basic` worked, but the equivalent for
  unencrypted traffic kept saying "path does not exist" — the `WSMan:` PSDrive was stale
  in that session. Bypassed it with the `winrm` CLI directly
  (`winrm set winrm/config/service/Auth '@{Basic="true"}'`).
- The property name itself was wrong in my first attempt (`AllowUnencryptedTraffic` isn't
  real on this WinRM version — the actual property is `AllowUnencrypted`). Found via
  `winrm get winrm/config/service` and corrected.
- From here on, drove everything via `pywinrm` from this side — no more manual typing
  needed in the RDP session.

### Installed Sysmon
Downloaded Sysmon + SwiftOnSecurity's public config directly on the box via
`Invoke-WebRequest`, installed as a service (`sysmon64.exe -accepteula -i`). Verified
immediately generating rich process-creation events (hashes, parent chains, command
lines).

### Wired Sysmon into the existing pipeline
Winlogbeat was already running (Application/Security/System/PowerShell channels) but
**not shipping Sysmon** at all. A first attempt to append the channel via regex
substitution accidentally **dropped** the "Windows PowerShell" channel entirely (a
backtick/`$1`-backreference escaping issue through nested bash→Python→PowerShell
quoting) — caught immediately by re-reading the output, fixed by rewriting the whole
config file cleanly instead of patching it. Also enabled **PowerShell Script Block
Logging** (event 4104) via registry policy — the channel was already configured in
Winlogbeat but the underlying OS policy to actually populate it wasn't on.

### Built the dashboard
**"Windows LAN Host - SOC Investigation Dashboard"** — 11 panels across auth (failed/
successful logons, logon type, privileged logons), process activity (creation timeline,
top images), and investigation (network destinations, registry persistence, scheduled
tasks/account changes, PowerShell script blocks, and a flagship "Suspicious Process/
Command Line Events" search).

**Two real KQL/query bugs found and fixed during live validation with the user watching:**
1. The Suspicious Commands panel used invalid KQL (wildcards wrapped around quoted
   phrases, e.g. `*"net user"*`) — Kibana's parser rejected it outright. Fixed by
   rewriting as valid unquoted wildcards / plain quoted phrases.
2. The Registry Persistence panel silently returned nothing despite the data existing.
   Root cause: `TargetObject` is a `text` field, and wildcard matching against `text`
   fields doesn't apply the field's analyzer to the search pattern — my mixed-case
   `*\Run\*` never matched the lowercased indexed tokens (and the literal backslashes
   don't even survive tokenization). Fixed by matching the `.keyword` subfield instead
   (exact case, true substring match). Verified directly against raw Elasticsearch before
   declaring it fixed.

### Validated 6 attack classes end-to-end
1. Registry Run-key persistence (Sysmon 13)
2. Simulated C2 network connection (Sysmon 3)
3. **Credential access simulation** — `reg save HKLM\SAM` / `HKLM\SYSTEM` — a genuine
   credential-dumping technique, **not blocked by Defender**, fully visible via Sysmon
   process creation with the exact command line.
4. Encoded PowerShell (`-EncodedCommand`) — executed cleanly, decoded content fully
   visible via script-block logging (4104), defeating the attacker's own obfuscation.
5. Backdoor local account creation + admin group add (4720/4732)
6. **Scheduled task persistence** — first attempt produced **zero** event (4698 never
   fired). Root-caused: "Other Object Access Events" audit subcategory is **disabled by
   default** on standalone Windows — a real, out-of-the-box detection gap for a common
   persistence technique (MITRE T1053.005). Fixed via `auditpol /set`, re-tested, event
   4698 now fires correctly.

### Bonus validation — the existing SOAR pipeline caught it live, unprompted
While testing, Badr independently showed a TheHive case that had been created
**automatically**: *"Windows Privilege Escalation"*, HIGH severity, TLP:RED, created by
the existing `ElastAlert-Windows` rule the moment our backdoor-account/admin-group-add
test landed in Elasticsearch. This is strong, unplanned end-to-end proof that the whole
chain (new host → Winlogbeat → Logstash → Elasticsearch → ElastAlert → TheHive) already
works together, not just the new dashboard in isolation.

## ✅ Task 3 — Suricata on the LAN interface (`em1`)

Added the third Suricata instance via the pfSense **GUI** (deliberately not a raw
config.xml edit — Suricata's package needs its own PHP sync/directory creation on save,
and this project has already had two outages from rushed raw XML edits to pf rules).
Walked the user through: Services → Suricata → Interfaces → Add → Logging tab (EVE JSON →
Redis, same `127.0.0.1:6379` list `suricata` as WAN/DMZ, so no ELK-side changes needed) →
Interface Settings (promiscuous mode on) → Categories (Select All, matching DMZ).

### pfSense had a connectivity wobble during activation
Tailscale briefly showed `active; relay, tx X rx 0` (same failure signature as two earlier
outages this project) right after the LAN interface was enabled. Resolved itself /
recovered without intervention this time — did not attempt any remote fix given the
history of that making things worse.

### Found and fixed a bigger bug while testing: Redis was down platform-wide
Initial LAN test scans produced zero events on `em1` — not even background traffic. Root
cause: **Redis wasn't running on pfSense** (`Connection refused` in the LAN Suricata
instance's own log) — a known recurring issue (Redis doesn't reliably survive a pfSense
reboot, and pfSense had just rebooted). Critically, **this was breaking WAN and DMZ
alerts too**, not just the new LAN instance — confirmed by finding the identical
`Connection refused` error in WAN's Suricata log. The whole SOC alert pipeline had gone
silently blind. User restarted Redis (`service redis start`); confirmed genuinely alive
via `ps` + a raw `PING`/`PONG` over the socket, despite `service redis status` continuing
to report "not running" — traced that specifically to a missing PID file the status script
depends on (a bookkeeping gap, not a functional one).

### Confirmed LAN capture works, alert-signature test deferred
After the Redis fix, a real background TLS flow from the Windows LAN VM
(`192.168.10.30` → `52.123.128.14`) was captured correctly on `em1` and reached
Elasticsearch — proving the full path (capture → Redis → Logstash → ES) works. Test scans
against pfSense's own LAN IP didn't register (self-addressed traffic likely doesn't hit
the promiscuous capture the same way pass-through traffic does on a virtual NIC). Did not
get to confirm a genuine `event_type: alert` signature match on LAN before the user asked
to pause — **deferred to next session**, once the LAN VMs are more reliably up.

### Also clarified for the user
The existing "IDS Detections Dashboard" is explicitly scoped to WAN+DMZ only (per its own
on-dashboard description) — it will not show LAN events until it's updated, and it filters
to `event_type: alert` specifically, so the LAN flow event we did capture correctly
wouldn't appear there even after that update.

## 🎤 Report angles unlocked today

- **"A bug I introduced while fixing a bug"**: my own backup file caused a platform-wide
  duplicate-event bug — a good, honest example of why temp/backup files need to live
  outside directories a service treats as config input.
- **"The status check lied, the protocol didn't"**: `service redis status` said "not
  running" while the process answered `PING` with `PONG` in real time — a clean example of
  verifying with the actual protocol/behavior rather than trusting a wrapper script.
- **"One misconfigured VM's clock corrupts a second, unrelated system's trust in its own
  data"**: same clock-drift bug class as before, now on a second host — worth noting this
  is a pattern (VM suspend, not reboot) rather than a one-off.
- **"Windows doesn't audit scheduled tasks by default"**: a completely realistic, common
  persistence technique (T1053.005) was invisible out of the box — found by testing, not
  assumed, and fixed with one `auditpol` command.
- **"The SOAR loop caught something we didn't even point it at"**: TheHive auto-created a
  real case from our Windows test traffic without any of today's work touching the SOAR
  side at all — strong, unplanned proof of an already-working automated response chain.
- **"A fragmented-packet corporate firewall policy masquerading as an app outage"**: what
  looked like "Kibana is down" for Badr was actually a network-layer MTU/fragmentation
  policy — a good example of not trusting the first, most obvious explanation for a
  symptom.
