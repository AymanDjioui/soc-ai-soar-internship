## 2. Injecting the synthetic alert — wrong endpoint on the first try

POSTed to `/api/v1/alert` first (TheHive 5's newer REST API) with an `artifacts` field
— alert created fine but `observableCount: 0`, the IP never actually attached as an
observable. TheHive's v1 API doesn't support embedding observables at alert-creation
time. Fixed by using the same **legacy `/api/alert` endpoint** that `HiveAlerter`
itself uses (confirmed from `configs/elk/elastalert/patches/thehive.py`, which POSTs
to `f'{hive_host}:{hive_port}/api/alert'`, no `/v1`) — that endpoint accepts the
`artifacts` array directly and correctly attaches the observable. Deleted the broken
first alert/case (my own test artifact, zero information value, not organic data —
different from the historical-noise cleanup in `notes/18.md` where deletion was
avoided for real data).

## 3. The real bug: taxonomies were being read from the wrong object

The already-running `soar-orchestrator.service` (dry-run) picked up the well-formed
alert and produced a verdict: **`BENIGN`, confidence 1.00, evidence: "All analyzer
reports show no taxonomies."** That evidence line is what gave the bug away — I could
already see via TheHive's `case/observables` query that VirusTotal *had* found
something (`1/91` + `8 malicious resolution(s)`). The evidence statement wasn't a
judgment call, it was factually wrong about what data existed.

Reproduced the exact call the orchestrator makes (`api.cortex.get_analyzer_job(job_id)`
via thehive4py, using the real job ID from the run) and printed the raw `report` dict.
It has exactly three keys: `success`, `full`, `artifacts` — **no `summary` key at
all**. Today's earlier fix (`notes/18.md` §6) read
`report.get("summary", {}).get("taxonomies", [])`, which silently returns `[]` on this
real shape every time, regardless of what the analyzer actually found. That fix had
only ever been tested against hand-written synthetic data shaped to an assumed schema
— never against a real live Cortex job — so the bug shipped invisibly. Every verdict
since that deploy (several hours of dry-run polling plus one prior test today) had been
running on zero evidence, which the system prompt correctly defaults to `benign` for
("no detections -> benign, don't escalate on absence of evidence") — except the
absence wasn't real, it was a parsing bug.

Found where the real data lives: `api.observable.get(observable_id)["reports"]`,
keyed by analyzer name, each with a `taxonomies` list — this matches exactly what
TheHive's own UI displays on the Observables tab. TheHive computes taxonomies
separately from the raw Cortex job and attaches them to the observable record, not to
the job status object.

**Fix** (`soar/e2e_soc_orchestrator.py`, the enrichment loop): analyzer jobs are still
created and waited on as before, but after all of an observable's jobs finish, the
observable is re-fetched once via `api.observable.get(obs_id)` and its `reports` dict
is used to build the `reports` list sent to the LLM, instead of trying to pull
taxonomies off each individual job's status response. Verified in three stages before
trusting it: (1) isolated call against the real job data matching the exact broken
shape, confirmed empty; (2) same call using the corrected `observable.get()` path,
confirmed real taxonomies returned, 840 byte payload; (3) fed the corrected data
through the actual `assess_enrichment()` LLM call — verdict flipped to `MALICIOUS`,
confidence 0.80, correctly citing the real VT evidence. Only then deployed (old version
backed up as `.bak-<timestamp>-taxonomy-bugfix`, checksums confirmed matching after
sync) and restarted the systemd service.

## 5. The armed run

Stopped the continuous dry-run systemd service first, to avoid a race where it might
consume the alert in dry-run before the deliberate targeted run did (`SOAR_ALERT_ID`
mode processes by ID regardless of status, so this wasn't strictly necessary, but
removed any ambiguity about which run actually acted). Created one more fresh alert,
same real IP and rich Cobalt Strike content. Ran manually,
`SOAR_DRY_RUN=0 SOAR_ALERT_ID=<id>` — a one-off targeted invocation, not a general arm
of the continuous service (that stays dry-run per the still-unanswered encadrant
question on autonomous vs. human-in-loop).

Result: `MALICIOUS`, confidence 0.90, `CONTAINMENT EXECUTED`. Verified independently
at the source, not just trusted the printed message (the project's own prior incident
was exactly an audit log claiming success when Cortex had rejected the job) —
`pfctl -t EasyRuleBlockHostsWAN -T show` on pfSense directly confirmed
`68.64.183.127` genuinely present. Audit log entry correctly shows
`"event": "containment_executed", "cortex_status": "Success"`. Restarted the dry-run
systemd service afterward.

Evidence captured (screenshots, by Ayman): the TheHive case (`~164106344`, #213) with
the full AI Triage Draft comment showing triage -> enrichment -> verdict -> containment
in one view; the pfSense table before (4 entries, IP absent) and after (5 entries, IP
present); the Observables tab showing the raw per-analyzer taxonomies and the
Responder Reports section (`PfSense_Blocker_1_0`, `Success`, exact timestamps).

**Scope note for the report:** this proves the autonomous *decision chain* end-to-end
(detection -> triage -> enrichment -> verdict -> guarded action), independently
verified at the firewall. It does not separately re-demonstrate "traffic from that IP
is now dropped" the way C-3's testmyids test did, since we don't control
`68.64.183.127` to send test traffic from it — that half of the claim (the block
mechanism itself drops real traffic) was already established by C-3.

The block was left in place rather than rolled back — `68.64.183.127` is a real,
currently-active malicious IP, so blocking it defensively is a correct outcome, not a
test artifact needing cleanup.
