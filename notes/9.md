Resume work after a few days' gap. Fix Logstash's broken state from the last session, get Juice Shop's HTTP logs flowing again (they'd stopped completely on 07-17), and clean up drift discovered along the way.

## ✅ What was accomplished

### 1. Logstash zombie-process issue — resolved itself / confirmed healthy

The container had been recreated (new container ID) since the last session and was processing events cleanly — no more `EADDRINUSE`/`event executor terminated` errors from the previous session's repeated restarts.

### 2. Suricata → Redis → ELK pipeline — found and fixed a real gap

Logstash was continuously failing to connect to Redis on pfSense (`Redis::TimeoutError`, repeating every ~11s). Checked pfSense: **Redis wasn't running** — didn't come back up after a reboot (pfSense had only ~2.5h uptime, someone had rebooted it since last session, unrelated to us). Started it (`service redis start` — note: pfSense's own status check misreports it as "not running" even when it's actually listening; `sockstat` is the reliable check). Confirmed Logstash reconnected immediately and Suricata alerts are flowing into `suricata-alerts-2026.07.20` again.

### 3. Juice Shop HTTP logs — root cause found: a direct consequence of the 07-17 Tailscale fix

`juiceshop-docker-*` indices stopped completely after 2026-07-17 — no logs for 3 days. Root cause: fixing the pfSense NAT issue on 07-17 required Badr to remove Tailscale from the Alpine/Juice-Shop VM entirely (he'd fully uninstalled it, not just brought it down — confirmed via `tailscale: not found`). But Alpine's rsyslog forwarder had been pointed **directly** at ELK's Tailscale IP (`100.99.54.59:5517`) as part of that same day's earlier work — so removing Tailscale from Alpine silently broke log shipping as a side effect of fixing the NAT path. Both fixes were correct in isolation; nobody connected the two before now.

**Fix**: rather than re-adding any VPN identity to Alpine (which is what caused the original NAT conflict), set up a plain TCP relay on pfSense using `socat`:
- Installed `socat` via `pkg install` on pfSense
- Relay listens on the DMZ-facing IP (`172.16.0.2:5517`, directly reachable from Alpine with no VPN needed) and forwards to ELK's Tailscale IP (`100.99.54.59:5517`)
- Updated Alpine's `/etc/rsyslog.d/docker.conf` omfwd target from `100.99.54.59` back to `172.16.0.2`
- Wrote a proper FreeBSD rc.d service script (`/usr/local/etc/rc.d/socat_juiceshop.sh`) and enabled it in `/etc/rc.conf.local` so the relay survives pfSense reboots — not left as an ad-hoc background process
- Verified end-to-end multiple times with uniquely-tagged test requests: Alpine → pfSense relay → ELK → Elasticsearch, confirmed working through the actual managed service (not just the initial manual test)

This is an application-layer relay, not a firewall/NAT rule — deliberately chosen to avoid touching pf rules again after how much trouble those caused in the previous session.

### 4. Alpine's system clock was stuck 3 days behind — found and fixed

While verifying the relay fix, noticed test events landing with a timestamp of `2026-07-17` despite being sent live on `2026-07-20`. Alpine's clock was frozen at the point it was last suspended in VMware (`uptime` showed ~9h47m, consistent with time-since-resume, not real elapsed time) — no NTP client had been running to correct it. This would have silently corrupted every timestamp from Alpine going forward, breaking any time-correlation with Suricata alerts.

**Fix**: one-time sync via `ntpd -q -p pool.ntp.org` (confirmed Alpine has outbound internet via pfSense's NAT), then enabled `ntpd` as a persistent OpenRC service (`rc-update add ntpd default`) so this doesn't recur after future suspends/reboots.

### 5. Verified the log-parsing fix from the previous session survived

The `juiceshop-docker` Logstash filter patch from 07-17 (parsing raw JSON directly instead of Badr's non-matching syslog-grok pattern) is confirmed still in place and working — fresh test docs show clean `access_log.status/request_uri/request_method` fields with correct timestamps.

## 🎤 Report angles unlocked today

- **"Fixes can have non-obvious side effects on shared infrastructure"**: solving the pfSense NAT/Tailscale conflict on 07-17 silently broke a completely different pipeline (Juice Shop log shipping) three days later, because both used the same VM's Tailscale identity for different purposes. A clean, concrete example of why distributed system changes need a mental map of *everything* depending on the thing you're changing, not just the immediate symptom.
- **"Preferring simpler failure modes"**: chose an application-layer relay (`socat`) over another firewall NAT rule specifically *because* of the previous session's pf/Tailscale fragility — a deliberate risk-reduction decision, not just "the first thing that worked."
- **"Silent data corruption is worse than an outage"**: the stuck clock wouldn't have caused any visible failure — logs would have kept flowing, just with wrong timestamps, silently poisoning any time-based correlation or dashard until someone noticed by chance. Good example of a class of bug that's more dangerous than a loud failure precisely because nothing looks broken.
