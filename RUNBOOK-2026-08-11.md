## Phase 1. C-1, the successful autonomous block (90 min) **PRIORITY**

### The problem this solves

`policy_guard()` refuses RFC1918 and Tailscale addresses, and nearly all your lab attacks
come from Tailscale. To demonstrate a *successful* block you need an attack whose
attacker observable is a genuinely external, routable IP.

**Use testmyids.** Your test case 01 already produces one.

### 1.1 Safety checks before arming

```bash
ssh djiouiayman@100.90.228.58
cd ~/soar

# confirm the kill switch path, then prove it works
touch KILL_SWITCH
./.venv/bin/python -c "
import os,sys; os.environ['THEHIVE_API_KEY']='t'; sys.path.insert(0,'.')
import e2e_soc_orchestrator as o
print('switch:', o.KILL_SWITCH_FILE, 'active:', o.kill_switch_active())
print(o.containment_allowed('45.155.205.211', 0.95))"
rm KILL_SWITCH
```

Expect `active: True` and a REFUSED result while the file exists.

Agree with Badr **now** how to remove a block:

```sh
# on pfSense, list and remove the easyrule entry
pfctl -t easyrule -T show
pfctl -t easyrule -T delete <IP>
```

### 1.2 Fire the attack

From the Windows or Linux LAN VM:

```bash
curl http://testmyids.com
```

Suricata should fire `GPL ATTACK_RESPONSE id check returned root`
(SID 2100498) with **src_ip 217.160.0.187**, which is external and routable.

Confirm the alert reached TheHive before running the orchestrator.

### 1.3 Run it ARMED

```bash
cd ~/soar
export THEHIVE_API_KEY='<key from Badr, do not paste into any file>'
./.venv/bin/python e2e_soc_orchestrator.py
```

You must see the banner:

```
*** CONTAINMENT IS ARMED — this run can modify the firewall ***
```

If you do not see it, `SOAR_DRY_RUN` is still set. Unset it.

Stop it with Ctrl+C once the target alert is processed, or `touch ~/soar/KILL_SWITCH`
from any directory to halt containment immediately.

### 1.4 Capture, in this order

1. The TheHive alert
2. The case created from it
3. The `AI Triage Draft` comment showing verdict, confidence and MITRE technique
4. The audit log lines:
   ```bash
   grep -E 'triage_complete|verdict_complete|containment_executed' ~/soar/soar_audit.jsonl
   ```
5. **The pfSense rule that appeared** (`pfctl -t easyrule -T show`)
6. **Proof the traffic actually stopped**: run `curl http://testmyids.com` again and show
   it failing

Item 6 is the one people forget. Showing that a rule was created is not the same as
showing that traffic was blocked. Do both.

### 1.5 Then undo it

Remove the block so testmyids stays usable for later tests.

## Phase 4. A-1b, Redis surviving a pfSense reboot (30 min) **DO LAST**

This reboots pfSense and takes the whole lab down. Do not do it before C-1 and C-2 are
captured.

```sh
# on pfSense, before rebooting: is Redis set to start on boot?
grep -r redis /etc/rc.conf.local /cf/conf/config.xml 2>/dev/null
```

Reboot, then verify without touching anything:

```sh
redis-cli -h 127.0.0.1 ping          # expect PONG
redis-cli -h 127.0.0.1 llen suricata # should not grow without bound
```

Then confirm `suricata-alerts-*` resumes in Elasticsearch on its own.

If Redis does not come back, add it to `/etc/rc.conf.local` and repeat the reboot until it
survives unaided. Redis has died silently three times in this project, so a fix that is
not proven by an actual reboot is not a fix.

## If something goes wrong

| Symptom | Cause and fix |
|---|---|
| `soc-logs-*` empty | syslogd stopped. `pfSsh.php playback svc restart syslogd`. Never `killall -HUP` |
| `suricata-alerts-*` empty | Redis on pfSense. `redis-cli ping`, restart it |
| First LLM call takes 30 s | normal cold start, warm it and retry |
| LLM call fails entirely | GCP VM stopped, or `OLLAMA_TIMEOUT` too low |
| Orchestrator blocks nothing | check the banner said ARMED, and that the attacker IP is external |
| It blocked something it should not | `touch ~/soar/KILL_SWITCH`, then `pfctl -t easyrule -T delete <IP>` |
